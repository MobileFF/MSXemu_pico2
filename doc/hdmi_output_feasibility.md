# PICO-HDMI-PLUS による HDMI出力 実現可能性調査

**ステータス: 完成。Phase 1・Phase 2・Phase 3とも実装・実機確認済み。本体Pico2のMSX実映像をHDMI側へ表示できることを確認した(`config.txt`の`hdmi=1`でopt-in)。長らく未解決だった「数十秒〜数分でHDMI信号が失われる("NO SIGNAL")」問題も原因を特定し解決済み(Core0のSPI受信割り込みハンドラ内に残っていたマーカー描画処理がHSTXのタイミングを妨げていた)、実機で30分以上の連続動作を確認済み。詳細な手順・設計・切り分け経過は `hdmi_bridge/README.md` と `doc/hdmi_bridge_phase2_report.md` を参照。既存の本体エミュレータのコード・ピン配置には変更を加えていない(基板を既に製作済みのため、既存のSPI1バス(GP10/11)を共有しGP28を新設CSとする方式を採用)。**

## 目的

[PICO-HDMI-PLUS](https://www.microfan.jp/2024/07/pico-hdmi-plus/)（microfan製、Raspberry Pi Pico/Pico W/Pico 2 に挿してHDMI出力できる拡張基板）を使い、本MSXエミュレータの映像をHDMI出力できないか検証する。現在のPico2（エミュレータ本体）はGPIOが全て使用済みのため、**PICO-HDMI-PLUS専用にもう1台Picoを追加する**前提。

## 調査結果

### 1. ハードウェア面：GPIO競合なし（確認済み）

PICO-HDMI-PLUSは完全に別チップの新規Picoに挿す構成のため、既存のエミュレータ用Pico2のGPIO逼迫とは無関係。

- 公式ページ記載のPicoDVI用固定ピン：`GP12`〜`GP19`（8本、TMDS差動3ペア: D0+/D0-, CK+/CK-, D1+/D1-, D2+/D2-）
- 基板搭載のタクトスイッチ4個・圧電スピーカーが一部GPIOを使用
- **自由に使えるGPIOとして公式に案内されているのは `GP0〜GP7`, `GP22`, `ADC0〜2`（`GP26〜28`）の計12本**（本体Pico2との通信用インターフェースをここに実装できる）
- 対応チップ: Pico / Pico W / **Pico 2** いずれも可（Pico 2を使えばRAM 520KB・CPU性能に余裕があり有利）
- 対応解像度: 320×240 @60Hz が確認できた（現在のMSX画面 256×192 を中央表示するのにちょうど良いサイズで、既存のILI9341運用と同じ考え方が使える）

### 2. ソフトウェア面：既製の「2台間ブリッジ」機能は存在しない（重要な訂正）

調査当初、Web検索で「別のPicoがSPI経由でST7789/ILI9341 TFTのふりをしてコマンドを受け、それをDVI出力に変換する」機能があるかもしれないという情報が得られたが、**公式リポジトリ [Wren6991/PicoDVI](https://github.com/Wren6991/PicoDVI) のソースツリーを直接確認した結果、そのような機能は存在しないことを確認した**（`software/apps/`配下の全サンプル・`software/libdvi/`のソース一覧を確認したが、SPI/ST77xx/ILI9341関連のファイルは一切なし）。この情報は誤りとして扱う。

実際のPicoDVIの設計は：
- **単一チップ内で完結**：Core1がRAM上のフレームバッファをTMDS(HDMI)信号へエンコードし続け、Core0がアプリとしてそのフレームバッファに書き込む、という構成。
- チップをまたいだ映像データ転送の仕組みは提供されていない。

→ **本体Pico2からHDMI側Picoへフレームデータを渡す通信部分は、自作する必要がある。** 単純な基板追加では済まず、HDMI側Pico用に新規ファームウェア（PicoDVIのフレームバッファAPIを使いつつ、受信処理は独自実装）を書く小規模プロジェクトになる。

### 3. HDMI音声は非対応

PicoDVI（バンドウィズ節約のためビット単位でTMDSを生成する軽量実装）にはHDMIオーディオ（データアイランド）を送る機能はない。README等にaudio関連の記載なし。**音声は引き続き既存のPWMブザー出力を使う前提**とする（HDMIケーブル経由でモニタのスピーカーから音を出すことは基本的にできない）。

## 結論

**実現可能性は高いが、「基板を挿すだけ」ではなく、HDMI側Pico用の新規ファームウェア開発を伴うサブプロジェクトになる。**

- ハードウェア的な制約・競合は無い（確認済み）
- 解像度・色深度もMSXの256×192には十分（確認済み）
- 最大の課題は **本体Pico2 → HDMI側Pico の映像データ転送の速度**。現行LCD（ST7796/ILI9341）向けSPI転送だけでも、実機検証の末41.67MHzを安定上限として約64fpsを達成した経緯があり（`project_msx_emulator`メモリ参照）、同程度かそれ以上のデータ量を新たな配線・新たなチップへ転送する場合、**FPSが現状より低下する可能性が高い**。実機での実測が必須。

## 実現のためのプラン（段階的）

### Phase 0: 部材調達
- PICO-HDMI-PLUS ×1
- Raspberry Pi Pico 2 ×1（HDMI出力専用。RAM/CPU余裕のためPico 2を推奨）
- HDMI対応モニタ・ケーブル
- 本体Pico2 ⇔ HDMI側Pico2間の配線材（信号線 4〜9本程度＋GND、電圧レベルは双方3.3Vなのでレベル変換不要）

### Phase 1: HDMI側単体の動作確認（コード改造なし）
PICO-HDMI-PLUSに既製のPicoDVIサンプル（Arduino/CircuitPython）をそのまま書き込み、モニタにHDMI出力できることをまず確認する。ここでは本体Pico2とは未接続。

### Phase 2: 受信インターフェースの試作
HDMI側Picoに、`GP0〜7`（8bitパラレル）または`GP0〜7`の一部を使ったSPIスレーブ受信の最小実装を追加し、外部から送ったテストパターン（単色・グラデーション等）をフレームバッファへ書き込んでHDMI表示できることを確認する。この時点ではPicoDVI公式サンプルの改造として、本体プロジェクトとは別のミニプロジェクト（別リポジトリ/別ビルド系統）として開発するのが安全。

通信方式は2案を比較検討：
| 方式 | 配線本数 | 想定スループット | 実装コスト |
| :--- | :--- | :--- | :--- |
| SPI（マスター送信） | 4本（SCK/MOSI/CS/DC相当） | 現行LCD運用の実績から類推し、実測 30〜40MHz程度が現実的上限か | 低（既存のSPI送信コードを流用しやすい） |
| 8bitパラレル＋PIO | 9〜10本（データ8本＋クロック/ラッチ） | SPIより高スループットが期待できる | 中（送受信ともPIOを新規に書く必要） |

まずSPIで動作させ、FPSが不足する場合にパラレル化を検討する、という順序を推奨（既存のSPI実装資産を再利用でき、着手が速いため）。

### Phase 3: 本体Pico2側の送信コード追加
`msx_core.c`に`msx_render_to_hdmi_pico()`のような新規関数を追加し、既存の`msx_render_to_display_1to1()`と並行して（またはconfig.txtで切り替えて）HDMI側Picoへフレームを送信する。既存のLCD切替（`lcd=ILI9341`/`ST7796`）の仕組みを踏襲し、`display=HDMI`のような切替オプションとして実装するのが自然。

### Phase 4: 性能検証・チューニング
実機でFPSを計測し、目標（現行LCD運用の63.9fpsに近い値、最低でも実用上ゲームが遊べる20〜30fps以上）に届くか確認する。届かない場合の対策候補：
- SPIクロックを段階的に上げ、信号品質が破綻しない上限を実機目視で確認する（LCD運用時と同じ手法）
- 差分転送（前フレームとの変更行のみ送る。MSXのBASIC画面やスクロールの少ないゲームで有効）
- パラレルバス化への切り替え
- HDMI側Picoの内部解像度・色深度を落として転送量を削減（例: 16bpp→8bppパレット化）

### Phase 5: 運用面の詰め
- LCDパネルとHDMIをどちらも使うか、HDMIのみに置き換えるかをユーザーが選択（config.txtでの切替を維持するのが柔軟）
- 音声は既存のPWMブザー経路を維持

## 未確定・要検証事項

- 通信リンクの実測スループットとそれに伴うFPS（現行LCDの63.9fpsに対しどこまで迫れるか）
- HDMI側Pico用ファームウェアの開発言語（pico-sdk(C) か CircuitPython か）— 本体側はMicroPython C拡張だが、HDMI側は独立チップなので言語を合わせる必要はない。PicoDVIの実績・サンプルの豊富さからは pico-sdk(C)ベースが情報量が多く手堅い
- 320×240以外の解像度・色深度オプションの詳細（製品ページの記載が簡略なため、実際にPhase 1で確認が必要）
