# HDMI出力サブプロジェクト Phase 1/2/3 実機検証レポート (2026-08-11)

`hdmi_bridge/`サブプロジェクト(PICO-HDMI-PLUS + 専用Pico2によるHDMI出力)の、Phase 1(HDMI単体動作)・Phase 2(本体Pico2との通信リンク)・Phase 3(本体エミュレータへの統合)実機検証結果のまとめ。経緯の全体像は `doc/hdmi_output_feasibility.md`、手順の詳細は `hdmi_bridge/README.md` を参照。

## 結論

- Phase 1・Phase 2・Phase 3すべて実装・実機確認済み。画質・フレームレート・配線方式(既存ピン変更なし)は要件を満たしている。
- **長らく未解決だった「数十秒〜数分でHDMI信号が失われる("NO SIGNAL")」問題は解決した(2026-08-11)。原因はCore0のSPI受信完了割り込みハンドラ内にわずかに残っていた描画処理(マーカー表示用のmemset)で、これがHSTXの走査線再設定タイミングを妨げていた。詳細は下記「【解決】NO SIGNAL問題」の節を参照。修正後、実機で30分以上の連続動作でNO SIGNALが発生しないことを確認済み。**
- 本体Pico2の既存ピン配置(GP10/GP11共有、GP28新設CS)を一切変更せずに実現できた。

## 構成

| | 本体Pico2 | HDMI側Pico2 |
|---|---|---|
| SCK | GP10(既存LCD/SDと共有) | GP2 |
| データ(MOSI→RX) | GP11(既存LCD/SDと共有) | GP0 |
| CS(新設) | GP28 | GP1 |
| GND | 共通GND必須 | |

HDMI側Pico2: `hstx/dvi_out_hstx_encoder`(公式pico-examples)ベースのHSTX DVI出力(640×480 RGB332) + SPI0スレーブ+DMAによる256×192画像受信。受信データは画面中央に描画、周囲は黒枠。

## 実機デバッグで判明した重要な知見

### 1. RP2350のSPIスレーブ(PL022)には既知の不具合がある

**CPOL=0/CPHA=0(SPIモード0)だと、CSアサート後わずか数バイト受信しただけで内部同期が崩れ、以降は完全に受信を停止する**(RXFIFOオーバーランフラグも立たない、静かに停止する)。この症状は配線・GPIO機能マッピング・DMA設定・DMAチャンネル優先度・ハードウェアSPI/手動ビットバンギングのどれを変えても再現し、Raspberry Pi公式フォーラムで同種の報告(モード0だとPL022スレーブがまともに動かない)が複数見つかったことで特定できた。

**対策: CPOL=1/CPHA=1(SPIモード3)に変更することで安定して受信できるようになった。** マスター側(`test_sender.py`の`machine.SPI(polarity=1, phase=1, ...)`)・スレーブ側(`main.c`の`spi_set_format(spi0, 8, SPI_CPOL_1, SPI_CPHA_1, SPI_MSB_FIRST)`)の両方で設定を揃える必要がある。

### 2. 受信完了時のコピー処理はCore1にオフロードする必要がある

Core0のSPI受信完了割り込み内で256×192(49,152byte)のmemcpyを行うと、HSTXの走査線再設定(約32マイクロ秒周期)を圧迫し、HDMI同期が完全に失われる(モニタが「NO SIGNAL」になる)ことを実機で確認した。

対策として、SPI受信用バッファをダブルバッファ化(`scratch_buf[2][...]`)し、DMA受信完了時はバッファの切り替えとDMA再アームだけをCore0(ISR内)で行い、実際の画面バッファへのコピーはCore1(`multicore_launch_core1`で起動)が担当する設計にした。これによりCore0はHSTXの実時間性を一切妨げられなくなった。

### 3. ボーレートと安定性は単純比例しない

実機での速度ごとの結果:

| ボーレート | fps(概算) | 結果 |
| :--- | :--- | :--- |
| 1MHz | 3 | 右端付近に軽微な位置ズレ |
| 5MHz | 13 | 1列分の位置ズレ |
| **10MHz** | **21** | **ズレなし・安定(推奨)** |
| 20MHz | - | 希に1バイト取りこぼしが起き、画像が横スクロールする |

「速いほど不安定になる」という単純な関係ではなく、10MHzが5MHzより安定するという非直感的な結果が出ている。根本原因は未解明。現状は実用上10MHzを推奨設定としており、深追いはしていない(Phase 4のチューニング時に再調査の余地あり)。

## デバッグ手法についてのメモ

オシロスコープが手元になく、本体Pico2側もREPL経由の手動操作という制約下で、以下の手法の組み合わせが原因特定に有効だった。

- **画面の隅に受信状態を色で表示するマーカー**: DMA受信完了ごとのトグル(左上)、GPIOの生電圧レベルのスナップショット(右上)、DMA残り転送カウントの変化(左下)。オシロなしでも「信号は届いているか」「SPIペリフェラルは実際に受信できているか」を視覚的に切り分けられた。
- **HDMI側Pico2自身のUSB CDCシリアル**からのデバッグprintf出力(`isr_count`/`dma_count`/SPIステータスレジスタ`sr`/`ris`の値)。数値で正確な状態を把握でき、色マーカーだけでは分からない詳細(RXFIFOオーバーランの有無等)を確認できた。
- **切り分け用の診断ビルド**(SPI受信を無効化してHSTX単体を確認する版、DMAの受信目標バイト数を64バイトなど小さくして完了頻度を上げる版)を用意し、問題の切り分けを段階的に進めた。
- **ハードウェアSPIを使わない手動ビットバンギング送信**を実装し、「ハードウェアSPIマスターの信号品質の問題」なのか「もっと根本的な問題」なのかを切り分けた。

## Phase 3: 本体エミュレータへの統合(実装完了、既知の問題あり)

本体Pico2の`msx_render_to_hdmi()`(`src/msx/msx_core.c`)で、`framebuf`(RGB565)をRGB332へ変換しSPI1経由でHDMI側Pico2へ送信する。`config.txt`の`hdmi=1`でopt-in、デフォルトでは完全に無効(HDMIアドオンを持たないユーザーへの影響ゼロ)。実装の詳細・設定方法は`hdmi_bridge/README.md`のPhase 3節を参照。

### 実装過程で判明した点

- **`framebuf`のバイト順に注意**: `rgb888_to_565be()`が示す通り、`framebuf`はILI9341のSPI転送向けにバイトスワップ済み(ビッグエンディアン)のRGB565で格納されている。HDMI変換時にこれを考慮せず読むと、R/G/Bのビットが誤った位置に来て「白黒っぽい」色になる(実機で確認・修正済み)。
- **RAM予算に注意**: 変換用に256×192byte(49,152byte)のフル1フレーム分バッファを新規に確保したところ、MicroPythonのGCヒープを圧迫し起動時に`MemoryError`が発生した(実機で確認)。1行分(256byte)のバッファのみを確保し、CSをフレーム全体で保持したまま行ごとに逐次送信する方式に変更して解決。
- **ブロッキング送信のコスト**: `msx_render_to_hdmi()`はブロッキング実装で、10MHzで約40ms/フレームかかる。毎フレーム送信するとFPSが約44→17まで低下した(実機で確認)。`hdmi_frame_skip`(デフォルト2、Nフレームに1回送信)と、LCD/HDMIを排他にできる`display=lcd|hdmi|both`設定を追加して緩和している。

## 【解決】NO SIGNAL問題 (2026-08-11)

実機で、HDMI側PicoがSPI0スレーブ受信を行っている間(本体からの送信の有無・方式によらず)、**数十秒〜数分程度でHDMI信号が失われる**現象が長らく発生していた。以下、切り分けの経過と最終的な解決内容。

### 切り分けの経過(いずれも改善に至らなかった、または悪化した対策)

| 試した対策 | 結果 |
| :--- | :--- |
| Phase 3統合(`display=both`、SPIモード毎フレーム切替) | 数分でNO SIGNAL。LCD側も巻き込まれ最終的に白画面化 |
| SPI周りの完全リセット(`spi_init()`で毎回ハードウェアリセット) | 改善せず。むしろHDMI画像が横に約100pxズレる新たな症状、LCD最上部のちらつきが発生し、悪化と判断し撤回 |
| `display=hdmi`(SPIモード切替がほぼ発生しない排他モード) | 約2分30秒でNO SIGNAL。`display=both`とほぼ同じタイミングで失敗し、**モード切替の頻度は原因ではないと判明** |
| Phase 2単体テスト(本体統合を完全に排除、`test_sender.py`のみ) | 約3〜5分30秒でNO SIGNAL。**Phase 3の統合とは無関係に、Phase 2の時点から潜在していた問題と判明** |
| HSTX単体(SPI受信を完全に無効化した診断ビルド) | 10分以上、問題なし。SPI受信が無効なら発生しない(→原因はSPI受信側にあると絞り込めた) |
| SPI受信DMAチャンネルの高優先度設定を撤去 | 改善せず(約4分40秒でNO SIGNAL) |
| Core1のビジーポーリングをSDK標準のコア間FIFO(`multicore_fifo_push/pop_blocking`、アイドル時はCore1が真にスリープ)に変更 | 改善せず(約3分20秒でNO SIGNAL) |
| システムクロックを126MHzに設定し、TMDSビットクロックを公式サンプルの近似値(250Mbps)から正確な252Mbpsに補正 | 悪化(約1分でNO SIGNAL)。撤回 |
| 別のモニタでの検証 | 数十秒でNO SIGNAL(元のモニタより早い)。モニタの同期喪失検知の感度差が症状の速さに影響していただけで、原因そのものではなかった |
| Pico2間の配線 | 既にはんだ付け済みのケーブルで接続されており、ブレッドボード起因の接触不良ではないと確認済み |

### 根本原因

**`spi_rx_dma_irq_handler()`(Core0のSPI受信完了割り込みハンドラ)内に、受信状態を目視確認するためのマーカー描画(`memset`によるごく小さな書き込み、16×16px)がまだ残っていた。** 49,152byteのフルコピーは既にCore1へオフロード済みだったが、この小さな描画処理自体はCore0のISR内に残っており、HSTXの走査線再設定(約32マイクロ秒周期)をわずかに、しかし長時間の累積で問題になる程度に妨げていた。

**対策: このマーカー描画もCore1側(FIFO経由でSPI受信完了通知を受けた後)へ移し、Core0のISRを本当に最小限(DMAバッファの切り替え・再アーム・Core1へのFIFO通知のみ)にした。** これにより実機で**30分以上の連続動作でNO SIGNALが発生しない**ことを確認した(受信データの中身も、固定テストパターンとの照合により正しいままであることを別途確認済み)。

### 教訓

Core0のSPI受信完了割り込みハンドラは、**どんなに小さな処理であっても「何かを描画・コピーする」処理を一切含めてはならない**。DMAバッファの切り替えとCore1への通知(`multicore_fifo_push_blocking`)だけにとどめ、実際のデータ処理(コピー・変換・検証等)はすべてCore1側で行うこと。「Core1にオフロードした」つもりでも、ISR内に副次的な描画処理が少しでも残っていると、今回のように数分〜数十分単位でしか症状が出ない、切り分けの難しい不具合になり得る。

## Phase 4: パレット化による転送量半減(2026-08-12、ビルド確認済み・実機確認待ち)

NO SIGNAL問題解決後の性能チューニングとして、MSX1のVDPが16色固定パレットしか持たないことを利用し、1ピクセル1byte(RGB332)ではなく1ピクセル4bit(パレット番号)で送る方式に変更した。送信量は49,152byte/フレーム→24,576byte/フレームへ半減する見込み。パレット本体は起動時に1回だけ送信し(ヘッダーで種別を区別するパケットプロトコルを新設)、フレームごとに送るのは番号のみ。設計・プロトコル詳細は`hdmi_bridge/README.md`の「Phase 4」を参照。送受信双方の新firmwareはビルド成功を確認済みだが、**実機での動作確認(色味・フレームレート計測)はまだ行っていない**。

## Phase 5: 送信側DMA化と10MHzでのパレット化けの発見(2026-09-04)

### ブロッキング送信のコスト(実測確認)

`msx_render_to_hdmi()`はブロッキング実装(`spi_write_blocking()`を192行分individually呼ぶ)で、10MHzで約40ms/フレームかかり、毎フレーム送信するとFPSが約44→17まで低下することを実機で確認した(既存の`hdmi_frame_skip`による緩和のみで、送信そのものを軽くする対策は未着手だった)。

### 対策: DMA化

1フレーム分(24,576byte)を静的バッファ(`hdmi_frame_buf_pal4`)へ一括で構築してから、LCD側`msx_render_to_display_1to1()`と同じ「DMA起動→即座に戻る」パターンで1回のDMA転送にまとめた。LCD/HDMIは物理的に同じSPIバス・同じDMAチャンネルを共有しているため、どちらが先に使っても安全なよう、共通の待機処理(`_spi_dma_wait()`)を両方の描画関数に追加した。

### 実機検証で判明した既存の問題: 10MHzでのパレット化け

DMA化後の実機テストで、**白のはずの箇所が緑になる**など、パレット参照が化ける症状が判明。当初はDMA化(転送が完全に途切れなくなったことによる電気的マージン不足)を疑ったが、DMA化**前**のブロッキング版でも同じ条件(10MHz)で再現することを確認し、**DMA化とは無関係の、この配線における10MHzでの既存の電気的限界**と判明した(Phase 4で「実機での色味確認はまだ」と記載した通り、この経路は今回初めて実機で詳しく検証された)。

5MHzに下げたところパレット化けは解消し、DMA版で52〜60FPSを達成(5-10MHzの間での安全な上限の絞り込みは今後の課題)。`mp/main.py`の`HDMI_BAUD`デフォルトを10MHzから5MHzへ変更した。
