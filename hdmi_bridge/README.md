## Phase 1: HDMI出力単体動作確認（完了）

実機で8色カラーバー表示を確認済み(GP12-19のHSTX/DVI配線、D0=赤/CK=クロック/D2=青/D1=緑のチャンネル割り当てが正しいことも確認済み)。

目的: PICO-HDMI-PLUS + Pico 2 だけでHDMI出力できることを確認する。本体Pico2とは無接続。

### 手順

1. **CircuitPythonの書き込み**
   - https://circuitpython.org/board/raspberry_pi_pico2/ から最新の安定版UF2をダウンロード（汎用の「Raspberry Pi Pico 2」用。PICO-HDMI-PLUS専用のビルドは無いので汎用版でよい）
   - Pico 2の **BOOTSELボタンを押しながら** USB接続 → `RPI-RP2` という名前のドライブが出現
   - ダウンロードしたUF2ファイルをそのドライブにコピー(ドラッグ&ドロップ)
   - 自動的に再起動し、`CIRCUITPY` という名前のドライブとして認識されればOK

2. **テストコードの配置**
   - このディレクトリの `phase1_test/code.py` を、`CIRCUITPY` ドライブの **ルート直下** にそのままコピー(ファイル名は`code.py`のまま。CircuitPythonは`code.py`を自動実行する仕様)

3. **配線・実機確認**
   - Pico 2をPICO-HDMI-PLUSのソケットに挿す(向き注意)
   - PICO-HDMI-PLUSのHDMIコネクタとモニタをHDMIケーブルで接続
   - USB給電(Pico 2側のUSBでもPICO-HDMI-PLUS側の給電経路でもどちらでも可)
   - モニタの入力切替をそのHDMIポートに合わせる

4. **期待される結果**
   - 画面に8色の縦カラーバー(白/黄/シアン/緑/マゼンタ/赤/青/黒)が表示されればHDMI出力自体は成功
   - **色の並び順がおかしい場合**（配線は合っているのに色だけ変な場合）は配線ミスではなく、コード内の `red_dp/red_dn` `green_dp/green_dn` `blue_dp/blue_dn` のGPIO割り当て(D0=赤/D1=緑/D2=青という仮定)が実際の基板と違う可能性が高い。`code.py`冒頭のコメント通り、GP16/17とGP18/19の組を入れ替えて再試行する

### うまく映らない場合の切り分け

- 何も映らない/モニタが信号を検出しない → まずPico 2がきちんとPICO-HDMI-PLUSに挿さっているか、HDMIケーブル・モニタ入力切替を再確認
- CIRCUITPYドライブに`code.py`を置いた直後にドライブが認識されなくなる/再起動を繰り返す → コード内のエラーの可能性。`CIRCUITPY`ドライブ直下に自動生成される`boot_out.txt`や、シリアルコンソール(`screen`や`mpremote`等でPico 2のUSB CDCに接続)でエラーメッセージを確認する

## Phase 2: 受信インターフェースの試作（進行中）

目的: 本体Pico2 → HDMI側Pico2への映像データ転送リンクを試作し、テストパターンが正しい位置・タイミングで表示できることを確認する。**まだ本物のMSX映像は使わない**単体テスト。

### 採用した方式(pico-sdk C, Option A)

Phase 1のCircuitPythonコードは「配線とHSTXチャンネル割り当てが正しい」ことの検証役として役目を終え、Phase 2からはRaspberry Pi公式`pico-examples`の`hstx/dvi_out_hstx_encoder`をベースにしたpico-sdk(C)実装に切り替えた。理由:
- 公式サンプルのピン配置(GP12-19)がPhase 1の実機確認結果と完全一致
- HSTX+DMAがハードウェアでスキャンアウトを行うため、CPU(Core0/Core1とも)がほぼ丸ごと空く。SPIスレーブ受信をここに追加しても性能的な取り合いが起きない
- CircuitPythonでのPython経由のピクセル書き込みに比べ、C側でDMA直結にできるため高速

### 配線

本体Pico2側の**既存LCD/SD用SPI1バス(GP10=SCK, GP11=MOSI)をそのまま共有**し、CS線だけ新設(GP28)する方式を採用(基板を既に製作済みで既存ピン配置を変更したくないという制約のため)。

| | 本体Pico2 | HDMI側Pico2 |
|---|---|---|
| SCK | GP10 (既存LCD/SDと共有) | GP2 (SPI0 RX相当の受信専用ブロック) |
| データ | GP11 (既存LCD/SDと共有、MOSI) | GP0 (SPI0 RX) |
| CS(新設) | GP28 | GP1 (SPI0 CSn) |
| GND | 共通GND必須 | |

**既知のリスク**: このSPI1バスはLCD/SDカードと共有のため、過去にメガロム対応時のバス競合クラッシュ(`project_msx_emulator`メモリ参照)を起こした経路と同じ。Phase 2の単体テストではLCD/SDへ同時アクセスしないため問題は起きないはずだが、**Phase 3で本番の`main.py`ループに統合する際は、SPI1バスへのアクセスを排他制御する対策が必須**(既存の`msx_wait_display()`のようなbusyチェックの仕組みを、HDMI送信にも適用する)。

### プロトコル・ファームウェア設計

- HDMI側Pico2: 640×480@60Hz RGB332のフレームバッファを起動時に1回黒で初期化(周囲の黒枠は以後書き換えない)。SPI0スレーブでCSが下がっている間の256×192(49,152byte)をDMAでダブルバッファへ受信し、受信完了ごとにCore1が画面中央の256×192ウィンドウへコピーする設計(`hdmi_bridge/phase2_receiver/main.c`)。送信データ量を最小化するため黒枠部分は毎フレーム送らない。
- コピー処理はCore1にオフロードしている。Core0のSPI受信完了割り込みでmemcpyを行うと、HSTXの走査線再設定(約32us周期)を圧迫しHDMI同期が丸ごと失われる(「NO SIGNAL」になる)ことが実機で確認されたため。

**実機で判明した重要な制約**: RP2350のPL022 SPIスレーブ実装は、CPOL=0/CPHA=0(モード0)だと数バイト受信しただけで同期が崩れて止まる既知の不具合がある(Raspberry Pi公式フォーラムで複数報告あり)。**CPOL=1/CPHA=1(モード3)を使うことで安定して受信できる**ことを確認済み(`main.c`/`test_sender.py`とも設定済み)。GPIO0-2のピン配置・DREQ方向・DMAチャンネル優先度・配線の導通はすべて問題なく、原因はこのSPIモードの制約だった。

**実機での性能**: 20MHzでは希に1バイト取りこぼしが起きて画像が横にスクロールする不具合が出るが、1MHzまで下げると安定する(ただし1MHzでは約3fpsが上限)。中間速度(5MHz/10MHz等)での実用上限は検証中。現状1MHzでも右端付近に軽微な位置ズレが残っている(要調査、Phase 3以降で対応)。

### 手順

1. **HDMI側Pico2にファームウェア書き込み**
   - `hdmi_bridge/phase2_receiver/hdmi_receiver.uf2` をビルド済み(`build.sh`で再ビルド可能)
   - Pico 2をBOOTSELモードでUSB接続し、`RPI-RP2`ドライブに`hdmi_receiver.uf2`をコピー(Phase 1のCircuitPythonを上書きする形になる)

2. **配線**
   - 上記表の通り3本(SCK/データ/CS)+GND、計4本を本体Pico2とHDMI側Pico2の間に配線
   - **本体Pico2側のGP28は新設**。既存のGP10/GP11(LCD/SD用配線)には触れない

3. **本体Pico2でテスト送信スクリプトを実行**
   - `hdmi_bridge/phase2_test_sender/test_sender.py` を本体Pico2のファイルシステムへ転送(`mpremote cp`等)
   - **先に`main.run()`など本番ループが動いていないことを確認**(動いていれば`machine.reset()`等でREPLを取り戻す。SPI1バスの排他制御はPhase 3で入れる予定のため、Phase 2ではバス上で他のアクセスと同時に走らせないこと)
   - REPLで以下を実行:
     ```python
     import test_sender
     test_sender.run()
     ```

4. **期待される結果**
   - HDMIモニタの画面中央に256×192サイズの8階調テストパターンが黒枠付きで表示される
   - REPLに`frames/sec (approx): NN`が定期的に表示される(概算送信フレームレート)

### 結果の報告(2026-08-10時点、Phase 2完了)

実機で通信リンクの疎通・安定動作を確認済み。**10MHzで約21fps、位置ズレ・ティアリングなく安定表示**(30秒〜1分の連続動作で確認)。これを現時点の推奨設定とし、`test_sender.py`のデフォルトも10MHzに変更済み。

速度ごとの実機結果まとめ:

| ボーレート | fps(概算) | 結果 |
| :--- | :--- | :--- |
| 1MHz | 3 | 右端付近に軽微なズレ |
| 5MHz | 13 | 1列分のズレ |
| **10MHz** | **21** | **ズレなし・安定** |
| 20MHz | - | 当時: 希に1バイト取りこぼし、画像が横スクロール |

**追記(2026-08-11)**: 上記20MHzでの不具合は、後に判明したCore0のSPI受信割り込みハンドラの問題(「【解決】NO SIGNAL問題」参照)が原因だった可能性が高い。その修正後、実機で改めて20MHzを試したところ異常なし(実機確認済み)。デフォルトは引き続き10MHzのまま(配線品質は個体差があるため保守的な値を既定値とし、`config.txt`の`hdmi_baud`で各自の環境に合わせて上げられるようにしている)だが、はんだ付け等の確実な配線であれば20MHzまで問題なく上げられる見込み。

速度と安定性が単純比例しない(5MHzより10MHzの方が良好)非直感的な結果が出ており、根本原因は未解明。実用上10MHzが安定しているため深追いはしていないが、Phase 4のチューニング時に再調査の余地あり。

**追記(2026-08-11): この「30秒〜1分の連続動作で確認」の後、SPI受信を有効にしたまま数分〜数十分稼働させるとNO SIGNALになる問題が見つかっていたが、原因を特定し解決済み(Core0のSPI受信割り込みハンドラ内に残っていたマーカー描画処理がHSTXのタイミングを妨げていた)。修正後は30分以上の連続動作を確認済み。詳細は`doc/hdmi_bridge_phase2_report.md`の「【解決】NO SIGNAL問題」を参照。**

## Phase 3: 本体Pico2側でMSXの実映像を送信する統合(実装・実機確認済み)

目的: 本体エミュレータ(`src/`, `mp/`)にHDMI送信を統合し、LCDに表示している実際のMSX映像をHDMI側Pico2へも送る。**デフォルトでは無効**(HDMIアドオンを持たないユーザーに一切影響しないopt-in設計)。

### 実装内容

- `src/msx/msx_core.c`: `msx_init_hdmi_output(msx, cs_pin, baudrate)` / `msx_render_to_hdmi(msx)` を追加
  - `msx_render_to_hdmi()`: `framebuf`(RGB565、ILI9341向けにバイトスワップ済みのビッグエンディアン格納 — 変換時に読み戻す必要がある点に注意)を1行(256byte)ずつRGB332に変換(R上位3bit/G上位3bit/B上位2bit)し、SPI1経由でブロッキング送信。CSをフレーム全体で保持したまま行ごとに逐次送信する(フル1フレーム分のバッファを持たない — RAM予算の都合、後述)
  - 送信直前に必ず`spi_set_baudrate()`/`spi_set_format()`でCPOL=1/CPHA=1・ボーレートを再設定(LCD側`msx_render_to_display_1to1()`が既にSD干渉に対して行っているのと同じ防御パターン。RP2350のPL022 SPIスレーブがモード0だと同期崩壊する既知の制約があるため、HDMI送信は必ずモード3を使う — `doc/hdmi_bridge_phase2_report.md`参照)
  - `hdmi_ready`フラグがfalse(`msx_init_hdmi_output()`未呼び出し)の間は完全に無効・無害
- `src/msx/modmsx.c`: `msx.init_hdmi_output(cs_pin, baudrate)` / `msx.render_to_hdmi()` をPythonへ公開
- `mp/main.py`:
  - `config.txt`に`hdmi=1`があるときのみ`msx.init_hdmi_output(28, 10_000_000)`を呼ぶ(GP28固定・10MHz固定)
  - `display=lcd|hdmi|both`(デフォルト`both`)でLCD/HDMIそれぞれの描画を独立にON/OFFできる。`hdmi_frame_skip`(デフォルト2)でHDMI送信の頻度を間引ける
  - メインループの`msx.wait_display()`(LCD DMA完全終了、SPI1バスがアイドル)の直後、次の`msx.render_to_display_1to1()`(LCD側設定を再適用)より前に`msx.render_to_hdmi()`を呼ぶ — LCDとHDMIの送信が同一SPI1バス上で絶対に重ならないよう厳密に直列化している

### 既知の制約・注意点

- **性能コスト**: `msx.render_to_hdmi()`はブロッキング実装(10MHzで49,152byte送信に約40ms)。毎フレーム送信するとFPSが約44→17まで低下することを実機で確認した。`hdmi_frame_skip`と`display=`設定で緩和可能
- **RAM予算**: フル1フレーム分の変換バッファ(49,152byte)を確保すると起動時に`MemoryError`になることを実機で確認した(現在は1行分=256byteのみ確保)。今後この経路にバッファを追加する場合は同じ罠に注意
- **SPI1バスの排他制御**: LCD/SDカードと共有バスのため、`wait_display()`後・次の`render_to_display_1to1()`前という厳密な順序を守っている。この順序を崩す変更をする場合は、過去のメガロム対応時のバス競合クラッシュ([[project_msx_emulator]]メモリ参照)を再発させないよう注意

### 設定方法

`/sd/msx/config.txt`に以下を追記:
```
hdmi=1
display=both
hdmi_frame_skip=2
hdmi_baud=10000000
```

HDMIアドオンを使わない場合は`hdmi=0`（あるいは行自体を省略）でよい。`hdmi=1`のまま`display=lcd`にする場合との性能差はない(`hdmi=1`はGP28のGPIO初期化を1回行うだけで、毎フレームのコストは`hdmi=0`と同じ)。

`hdmi_baud`はデフォルト10MHzだが、配線がしっかりしていれば(はんだ付け等)20MHzまで上げられる(実機確認済み、上記追記参照)。値を上げるほどHDMI送信の所要時間が短くなり、体感FPSも向上する。横方向のズレやチラつきが出たら一段階下げること。この設定はGUI+F7メニューには含まれていない(`config.txt`を編集して再起動が必要)。

### 結果の報告(2026-08-11時点)

実機でHDMI側に実際のMSX映像が表示されることを確認済み(色味も含め正しく表示)。長らく未解決だった「数分でNO SIGNALになる」問題も、`hdmi_bridge/phase2_receiver/main.c`側の修正(Core0のSPI受信割り込みハンドラからマーカー描画処理を除去)で解決し、30分以上の連続動作を確認済み。詳細は`doc/hdmi_bridge_phase2_report.md`を参照。

### GUI+F7メニューからのライブ設定(実装・実機確認済み)

エミュレータメニュー(GUI+F7)に「HDMI Settings」を追加した(`mp/msx_menu.py` / `mp/main.py`)。`hdmi`/`display`/`hdmi_frame_skip`の3つを**再起動なしで即座に**変更でき、ENTERで`config.txt`にも保存できる(既存の「Audio Settings」と同じ設計)。`config.txt`に`hdmi=1`を書いていなくても、メニューから初めてONにした場合はその場でGPIO初期化を行う。

実装過程で見つかった2つのバグと修正:

1. **メニュー画面自体がHDMIに表示されない**: 描画確定処理`MenuCanvas.flush()`(ROM選択画面・エラー画面・全メニューが共通で使う)が`msx.render_to_display_1to1()`(LCD)のみを呼び、`msx.render_to_hdmi()`を呼んでいなかった。ゲーム画面はHDMIに出るのに、メニューを開くとHDMI側は最後のゲーム画面のまま固まって見えていた。対策として`msx_menu.py`に`set_display_state()`を追加し、`flush()`もメインループと同じロジックでHDMIにも送信するようにした。
2. **`display=hdmi`のままHDMIをOffにすると画面が固まる**: `display`が`hdmi`(LCD不使用)の状態でHDMI設定メニューから「HDMI: On→Off」にすると、LCD・HDMIのどちらも描画対象でなくなり、画面更新処理が完全に無効化されていた(エミュレータ自体は動作し続けるため「画面だけ固まる」という分かりにくい症状になる)。対策として、**HDMIが実際に使えない状態なら必ずLCDにフォールバックする**セーフガードをメインループ・`MenuCanvas.flush()`の両方に追加した(`hdmi=0`のまま`display=hdmi`と設定してしまった場合も同様に自動でLCD表示に切り替わる)。

## Phase 4: パレット化によるHDMI転送量半減(実装完了・実機確認待ち)

目的: `msx_render_to_hdmi()`のブロッキング送信そのものの所要時間を短縮する。MSX1のVDP(TMS9918A)は**ハードウェア固定の16色パレット**しか持たない(ソフトウェアで変更不可)ことを利用し、1ピクセルあたり1byte(RGB332)ではなく1ピクセルあたり4bit(パレット番号、2ピクセル/byte)で送ることで、フレームあたりの送信量を49,152byte→24,576byteへちょうど半減させる。

### プロトコル設計

`display=hdmi_frame_skip`のような間引きとは別軸の高速化で、両立可能。設計方針は「パレットは滅多に変わらないので、フレームごとに送るのはパレットの**番号**だけにし、パレットの実体(RGB値)は起動時に1回だけ送る」というもの。CSが下がっている1回の送信バーストを「パケット」とし、先頭2byteをヘッダーにした:

| ヘッダー[0](種別) | ヘッダー[1](引数) | ペイロード | 用途 |
| :--- | :--- | :--- | :--- |
| `0x00` (PKT_PALETTE) | パレット色数(通常16) | RGB332 × N byte | パレット本体(起動時に1回、または変更時のみ) |
| `0x01` (PKT_FRAME_RAW332) | 未使用(0) | RGB332 × 49,152byte | 旧方式のフレーム(互換用、現行実装は送信しない) |
| `0x02` (PKT_FRAME_PAL4) | 未使用(0) | パレット番号(4bit×2/byte) × 24,576byte | 新方式のフレーム本体 |

- 送信側(`src/msx/msx_core.c`): `msx_init_hdmi_output()`が呼ばれた時点で`msx_send_hdmi_palette()`を自動的に1回実行(MSX1のパレットは起動後変わらないため、呼び出し側が明示的に呼ぶ必要はない)。`msx_render_to_hdmi()`は`framebuf`の各ピクセル(RGB565)を、既知の16色パレット(`msx->palette565[]`)と逆引き照合してパレット番号に変換し、2ピクセルを1byteに詰めて送信する。逆引きは「直前のピクセルと同じ番号か」を先にチェックしてから16件の線形探索を行う(単色の背景・枠線が多いMSXグラフィックスでは高速化に有効)
- 受信側(`hdmi_bridge/phase2_receiver/main.c`): SPI0受信DMAを「ヘッダー2byte受信→ペイロード受信」の2段階状態機械に変更。`PKT_PALETTE`受信時はパレットRGB332テーブルを更新するだけ(描画はしない)。`PKT_FRAME_PAL4`受信時はCore1側で2ピクセル/byteを展開しながらパレット変換してフレームバッファへ書き込む
- **`PKT_FRAME_RAW332`は「旧方式の後方互換用」ではなく、メニュー/UI画面用の現役の経路として使う**: `msx_render_to_hdmi_raw332()`(`src/msx/msx_core.c`)/`msx.render_to_hdmi_raw332()`を新設し、`msx_menu.py`の`MenuCanvas.flush()`から呼ぶようにした。理由は実機で発見: メニュー画面は同じC側`framebuf`に直接描画するが、枠線・ハイライト等でMSXゲーム画面の16色パレットに収まらない任意の色を使う。`msx_render_to_hdmi()`(PAL4)の逆引きは16色との完全一致でしかパレット番号を特定できないため、一致しない色はすべて黒にフォールバックしてしまい、実機で「メニューが黒と白しか表示されない」症状になった。ゲーム画面(`main.py`のメインループ)は必ず16色パレットの値しか持たないためPAL4のままで問題なく、メニューだけRAW332(パレット制約なしだが2倍のバイト数)に切り替えることで両立している

### 期待される効果

10MHzのままでも送信byte数が半分になるため、`msx_render_to_hdmi()`の所要時間(旧: 約40ms/フレーム)がおよそ半分(約20ms)になる見込み。`hdmi_frame_skip`を減らす(=HDMI更新頻度を上げる)余地が生まれ、BGMテンポの改善(ループ全体の速度低下軽減)にもつながる。**この効果はまだ実機で計測していない**(ビルド成功・受信側ファームウェア書き込み待ちの状態)。

### 実機確認の経過(2026-08-12)

1. 受信側・送信側とも新ファームウェアを書き込み、ゲーム画面のPAL4送信は正常動作を確認(色味も含め正しく表示)
2. **見つかったバグ1**: 受信側だけ旧ファームウェアのままだと、ヘッダー付きの新プロトコルを旧方式(ヘッダーなしRAW332固定長)として誤読し、画面が4分割・1/4サイズのタイル状に表示される。両方を新ファームウェアに揃えれば解消(単純な書き込み漏れだった)
3. **見つかったバグ2・修正済み・実機確認済み**: メニュー画面が黒と白しか表示されない症状。原因はメニュー(`MenuCanvas`)がゲーム画面と同じ`framebuf`に描画するが、MSXゲーム画面の16色パレットに収まらない任意のUI色(枠線・ハイライト等)を使っていたため。PAL4方式の逆引きロジックは16色との完全一致でしか変換できず、非一致色はすべて黒にフォールバックしていた。対策として`msx_render_to_hdmi_raw332()`(パレット制約なし、1byte/pixel)を新設し、`MenuCanvas.flush()`はこちらを使うよう分離した(ゲーム画面は引き続きPAL4)。
4. **フレームレート実測**: メニュー色バグ修正後、`hdmi_frame_skip=2`でFPS 40〜50台まで改善(Phase4以前は`hdmi_frame_skip=5`でようやく40〜50fpsだった)。Phase 4は実質完了。

## Phase 5: Core1非同期送信(2026-08-13、試みたが実機検証の結果撤回・削除済み)

Phase 4で転送量を半減させても、`msx_render_to_hdmi()`はまだブロッキング実装のため、毎フレーム「MSXエミュレーション計算(compute) + SPI送信(send)」を直列に払っていた。`framebuf`は元々ダブルバッファ(`msx_run_frame()`は常に`framebuf_ready_idx`と逆側のバッファに書き込む — LCD DMAと次フレーム計算を並行させるための既存の仕組み)なので、これをHDMI送信にも応用し、フレームNのSPI送信をCore1で行いながらCore0はフレームN+1の計算を並行して進める設計を試みた(毎フレームのコストを「compute+send」から「max(compute, send)」に短縮する狙い)。**実機検証の結果、複雑さとRAMリスクに見合う効果が得られなかったため、コードは完全に削除しロールバックした。** 以下は将来同じアプローチを再検討する際の教訓として残す。

### 実装していたもの(現在は削除済み)

- `src/msx/msx_core.c`: `msx_init_hdmi_async()` / `msx_render_to_hdmi_async_start()` / `msx_wait_hdmi_async()`。Core1で`hdmi_async_core1_loop()`を起動し、コア間FIFOで「送信するバッファ番号」を受け取ってPAL4送信。完了通知は最終的にFIFOではなく共有volatileフラグ方式に変更(下記の教訓2参照)
- `src/msx/micropython_msx.cmake`: `pico_multicore`をリンク(本体Pico2でCore1を使うのはこの機能が初めてだった)
- `mp/main.py`: `config.txt`の`hdmi_async=1`(`display=hdmi`のときのみ有効)でCore1送信を起動。セーブ/ロード・GUI+F7メニュー起動の直前に`msx.wait_hdmi_async()`でCore1の完了を待つガードを追加

### 実機検証で得た教訓(将来Core1を使う機能を追加する際に必読)

1. **MicroPython rp2ポートで`multicore_launch_core1()`は使えない**: ポート自体のビルド設定が`PICO_CORE1_STACK_SIZE=0`を指定している(Core1を通常使わない前提のため)ので、標準の`multicore_launch_core1()`は`PANIC: ... PICO_CORE1_STACK_SIZE == 0`で即座に失敗する。`multicore_launch_core1_with_stack()`を使い、スタックバッファを自前で用意する必要がある。
2. **Core1→Core0方向のコア間FIFOが実機で信頼できなかった**: Core1側で`multicore_fifo_push_blocking()`が正常にリターンした(自作のチェックポイント変数で確認済み)にもかかわらず、Core0側の`multicore_fifo_rvalid()`がデータなしと報告し続ける現象が再現した。原因は特定できなかったが、Core0→Core1方向(ジョブの受け渡し)と単純な共有volatile変数(チェックポイント読み取り)は確実に動作したため、完了通知を共有volatileフラグ方式に変更して回避した。**Core1→Core0方向のFIFOに頼る設計は要注意。**
3. **Core1がCore0と同時にXIPフラッシュキャッシュを取り合うと、SPI送信のバイト間隔が不安定になる**: 15MHz以上のボーレートで送信すると、受信側で画面が4分割・1/4サイズに破損する現象が発生した(以前受信側ファームウェアの不一致で見た症状と同じ見た目だが、今回は送受信とも正しいファームウェアだった)。RP2350の`BUSCTRL_BUS_PRIORITY_PROC1_BITS`でCore1のバス調停優先度を上げても改善せず、Core1のホットパス(送信ループ・パレット変換・SPI設定)を`__not_in_flash_func`でRAM常駐化することで解消した。**根本原因の推測**: Core0の重い並行処理(Z80/VDPエミュレーション)がXIPキャッシュを頻繁に入れ替え、Core1の(滅多に実行されない)送信ループ命令がキャッシュから追い出され、フェッチのたびにキャッシュミス(QSPIフラッシュ読み出し)が発生。10MHzではこの遅延が1行分の送信時間内に収まっていたが、15MHz以上では収まらずSPIバイト列にギャップが生じ、タイミングに敏感な受信側PL022 SPIスレーブが同期を崩したと考えられる。
4. **RAM常駐化(`__not_in_flash_func`)は`static inline`関数では要注意**: `static inline`関数に`__not_in_flash_func`を付けても、コンパイラがインライン展開すれば呼び出し元ごとに複製されRAMを消費する。実際、Core1送信ループ1関数だけで約1020byteのRAMを消費し、この上乗せだけで32KBのROM読み込みが`MemoryError`になった。RAM常駐化が必要なのは「行ごとに繰り返される、真にホットな」コードだけに絞り(1フレームに1回しか呼ばれない設定関数は`__attribute__((noinline))`でFlashに残すなど)、慎重に見極める必要がある。
5. **RAM節約とタイミング要件の両立が困難だった**: 上記4の対策でRAM常駐化した後は`MemoryError`が再発し、スタックサイズ削減(1KB→768B)や関数のnoinline化で数百byte単位の節約を試みたが、32KB前後のROM読み込みマージンを安定して確保できなかった。

### 最終判断: Phase 4に戻す

実機計測の結果:
- Phase 4(同期)@ 25MHz, frame_skip=2: **40〜50 FPS**、安定動作、RAM問題なし
- Phase 5(非同期)@ 10MHz(破損しない唯一のボーレート), frame_skip=2: **32〜43 FPS**(Phase 4より遅い)

複雑さ・実機デバッグコスト・RAMリスクに見合うだけの速度向上が得られなかったため、**Phase 5のコードは全て削除し、Phase 4(同期送信)の状態に戻した**。RAM使用量は削除後327104byteで、Phase 5着手前と完全に一致することを確認済み。今後さらなる高速化を検討する場合は、上記の教訓(特に3・4)を踏まえた上で再設計するか、他の方策(差分更新等)を検討すること。

### 将来SPI1バスを共有する新機能を追加する場合の注意

`msx_init_hdmi_output()`自体(起動時1回のGP28 GPIO初期化)は共有SPI1バス(GP10/GP11)に一切触れないため無害。影響が出るとすれば、毎フレーム呼ばれる`msx_render_to_hdmi()`が同じSPI1ペリフェラルを使っている点のみ。新機能もSPI1を共有する設計にする場合:

- 重要なのは「両方の機能を同時に有効化しないこと」ではなく、**SPI1バスへの実際の読み書きがコード上で時間的に重ならないこと**(LCDとHDMIの間で`wait_display()`を挟んでいるのと同じ考え方)
- 新機能専用のCSピンを新設し、送信前に毎回ボーレート・モードを再設定する
- メインループの中で、既存のLCD/HDMI転送が完全に終わったタイミングでのみ呼び出す(割り込み等で非同期にアクセスする設計は、過去のメガロム対応時のSPI1バス競合クラッシュと同じ危険がある)
- 別のSPIペリフェラル(SPI0等、未使用のGPIO)を使えるなら、そちらの方がこの制約自体を回避できてシンプル
