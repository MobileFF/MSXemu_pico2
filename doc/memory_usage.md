# メモリ使用量の内訳

Raspberry Pi Pico 2 (RP2350、リンカ上のRAM領域512KB、物理SRAM総量520KB) 上でMSX1エミュレータが何にどれだけメモリを使っているかを整理する。`msx_state_t`(§2)の内訳はソースコード(`src/msx/msx_core.h`/`.c`、`src/msx/tms9918/`、`src/msx/emu2149/`)から構造体サイズを直接計算した値(`sizeof()`を実機で出力して検証したものではなく、パディングにより数〜数十バイト程度前後する可能性がある)。静的領域合計(§4)は2026-08-17に実際にビルドしたログの実測値。GCヒープ単体の実測空き容量は§4末尾を参照。

## 1. 全体像

リンカのRAM領域(512KB)は、大きく3つの領域に分かれる。

| 領域 | サイズ | 内容 | 管理者 |
| :--- | ---: | :--- | :--- |
| 静的領域(`.data`+`.bss`) | 319.4KB(実測) | `msx_state_t`(約296.2KB、計算値)+MicroPythonランタイム本体等(約23.2KB) | リンカ(コンパイル時に確定) |
| Cヒープ | 64KB(固定、`MICROPY_C_HEAP_SIZE=65536`) | VDPコア・PSGコア・カートリッジROM | `malloc()`/`calloc()` |
| GCヒープ + スタック | 残り 約128.6KB(実測) | Pythonオブジェクト全般 | MicroPython GC |

```
512KB RAM(リンカ領域)
├─ 静的領域 (.data+.bss)        319.4KB (62%)  ← うちmsx_state_tが296.2KB(ダブルバッファ化されたフレームバッファが主因)
├─ Cヒープ (malloc/calloc)       64.0KB (12%)  ← VDP+PSG+カートリッジROM
└─ 残り(GCヒープ+スタック)       128.6KB (25%)
```

**最大の消費源は`msx_state_t`という1つのグローバル構造体**であり、Cヒープでもなく、そもそもMicroPythonのGCヒープでもない。この構造体はコンパイル時にサイズが固定される(`.bss`セクション)ため、実行時のメモリ確保失敗(`MemoryError`)には直接関与しないが、リンカのRAM領域(512KB)の過半数を最初から占有している。

## 2. 静的領域(`.bss`): `msx_state_t` の内訳

`src/msx/msx_core.h` で定義されているグローバル構造体1個(`msx_state`)がプログラム全体で唯一のインスタンス。

| フィールド | サイズ | 用途 |
| :--- | ---: | :--- |
| `framebuf[2][256×192]` (u16) | **192.0 KB** | 表示用フレームバッファ(ダブルバッファ)。**最大の単一消費項目** |
| `ram[0x10000]` | 64.0 KB | MSXスロット3(メインRAM) |
| `bios[0x8000]` | 32.0 KB | MSXスロット0(BIOS/BASIC ROM) |
| `disp_row_buf[2][4×384]` (u16) | 6.0 KB | 1.5倍拡大表示用ステージングバッファ(現状の本番描画パスでは未使用、拡張用に残置) |
| `audio_buf[512]` (i16) | 1.0 KB | PSGオーディオのリングバッファ |
| `scanline_buf[256]` | 0.25 KB | 1スキャンライン分の作業バッファ |
| `disp_col_src[384]` (u16) | 0.75 KB | 拡大表示用の列マッピングテーブル |
| `key_matrix[11]` ほか小フィールド多数 | 約0.1 KB | キーボード行列・スロット選択・SPI/HDMI設定・ジョイスティック状態など |
| `z80 cpu`(CPUコア本体) | 約0.07 KB | レジスタ・フラグ一式(無視できる規模) |
| `vdp`/`psg` ポインタ | 8 B | Cヒープ上のVDP/PSGインスタンスへのポインタ(実体は§3) |
| **合計** | **約296.2 KB** | |

**内訳の要点:**
- **`framebuf`のダブルバッファ化(192KB)が支配的**。表示DMA転送とZ80/VDPエミュレーションを並行実行するパイプライン設計のトレードオフとして、シングルバッファ(96KB)の2倍を消費している(2026-08-01のFPS改善作業で採用、詳細は`project_msx_emulator`メモリ参照)。
- `disp_row_buf`は元々1.5倍拡大表示(ST7796パネル用)のために32バッチ分(48KB)確保されていたが、GCヒープ圧迫が発覚し4バッチ分(6KB)に縮小済み。現在の本番描画は等倍パス(`render_to_display_1to1()`)を使うためこのバッファ自体使われていないが、将来の拡大表示再有効化に備えて残置されている。
- `bios`(32KB)+`ram`(64KB)の96KBはMSXのメモリマップそのものであり、これ以上削れない。

## 3. Cヒープ(`malloc`/`calloc`、64KB固定)

MicroPython RP2ポートはCの`malloc()`/`calloc()`用ヒープをデフォルト0バイトとするため、`bldfrm_msx.sh`が`MICROPY_C_HEAP_SIZE=65536`(64KB)を明示的に指定している。これを怠るとVDP/PSGの`malloc`がGCヒープ領域を静かに破壊し原因不明のハングを起こす(実際に踏んだバグ、`doc/build_guide.md`参照)。

| 消費者 | サイズ | 確保タイミング |
| :--- | ---: | :--- |
| VDPコア(`VrEmuTms9918`、`vram[16384]`が主体) | 約16.3 KB | `msx_init()`時に1回、以後解放されない |
| PSGコア(`PSG`構造体) | 約0.15 KB | `msx_init()`時に1回 |
| カートリッジROM | 最大 **32 KB** / スロット | ROM選択時(下記2モードのいずれか) |
| **常時消費**(VDP+PSG) | **約16.5 KB** | |
| **カートリッジ込みの実質使用**(1スロット時) | **約48.5 KB** | 64KB予算のうち残り約15.5KBが余裕 |

カートリッジROMの確保は`load_cart_smart()`がサイズに応じて自動選択する2モードだが、**どちらのモードでも最終的に64KB C ヒープを消費する**点は同じ:

- **フルRAMロード**(`msx_load_cart()`、非バンク切替・32KB以下向け): ROM全体を一度に`malloc()`。
- **メガロムページング**(`msx_load_cart_paged()`、128KB以上のバンク切替カート向け): 現在選択中の4バンク×8KB=**32KB固定**のキャッシュのみ保持(ROM実サイズに関係なく常に32KB)。実データはPico2内蔵フラッシュの`/megarom_cache.rom`から都度フェッチする。

いずれの場合もカートリッジ1本あたり32KBが上限となるよう設計されているため、VDP(16.3KB)+PSG(0.15KB)+カート(32KB)=約48.5KBで収まり、64KB予算に約15.5KBの余裕がある。

**⚠️ 既知のリスク**: カートリッジスロットは2つ(`cart[2]`/`cart_cache[2]`)存在し、**両スロットに同時にROMをロードした場合、単純計算で32KB×2=64KBとなりVDP/PSG分を合わせて約80.5KBとなって64KB予算を超過する**。マルチスロットカートリッジ(スロット2)は`project_msx_emulator`メモリの残タスクにある通り実機未検証であり、この構成でのメモリ超過リスクは未確認。実機検証時は`gc.mem_free()`だけでなくCヒープ枯渇によるハング(GCヒープ破壊と同じ症状)にも注意が必要。

### 3.1 2026-09-20更新: メガロムキャッシュに共有victimプールを追加、Cヒープを80KBに拡大

`doc/architecture.md`§「メガロムのFPS低下について」が報告した**キャッシュヒット率0%**の実機事例(少なくとも1タイトルでバンク切替のたびに毎回フェッチが発生)は、当時のキャッシュ設計が各ウィンドウにつき**1ページしか保持できなかった**(直前のページを即座に上書き)ことが原因と判明。2バンクの間を行き来するだけの典型的なパターンでも、切替のたびに必ずキャッシュミスになっていた。

**最初の対策(後に撤回)**: `MSX_CART_PAGE_DEPTH`を1→2にし、各ウィンドウ専用の2ページ目を追加(4窓×2ページ×8KB=64KB/スロット、+32KB)。ネイティブホストビルドでは2バンクping-pongが100%ヒットになることを確認できたが、この+32KBを確保するために`MICROPY_C_HEAP_SIZE`を65536→92160へ拡大したところ、GCヒープ側が圧迫され、**本件とは無関係な`mp/msx_mode_switch.py`の遅延コンパイルが実機で`MemoryError`を起こすようになった**(ランタイムメニューからカートリッジ/ディスクモード切替を選択すると発生)。CヒープとGC/Pythonヒープは同じ固定512KB SRAM予算を奪い合う関係にあるため、一方を大きく増やせば他方が犠牲になる。

**採用した設計**: 各ウィンドウ専用の2ページ目ではなく、**4ウィンドウが共有する小さな「victimプール」**を追加する方式に変更(`MSX_CART_VICTIM_SLOTS`、`src/msx/msx_core.h`)。あるウィンドウが立ち退かせたページを捨てずにこの共有プールへ退避し、次にどのウィンドウであってもそのページ番号が再要求されればそこから復元する(ROMのページ内容はどのウィンドウ経由でも同一なので、退避元のウィンドウを問わず共有できる)。ドキュメント化された「1ウィンドウが2バンクを往復する」パターンには共有スロット1つで十分効き、実機を待たずネイティブホストビルドのテストで(a)同一ウィンドウでのping-pongが100%ヒットになること、(b)異なるウィンドウ間でも退避ページが再利用されることの両方を確認済み。

初回は`MSX_CART_VICTIM_SLOTS=1`(+8KB)で導入したが、実機で「以前と比べ気持ちFPSが落ちている」との報告を受け、複数ウィンドウが同時にバンク切替する状況での共有スロット競合を緩和するため`2`(+16KB)に増量した。

メモリコストへの影響:

| 項目 | 変更前 | victim×1(暫定) | victim×2(採用) |
| :--- | ---: | ---: | ---: |
| `cart_cache[]`(1スロットあたり) | 32.0 KB (4窓×8KB) | 40.0 KB (+victim×1) | 48.0 KB (+victim×2) |
| `MICROPY_C_HEAP_SIZE`(`bldfrm_msx.sh`) | 65536 (64.0 KB) | 73728 (72.0 KB) | 81920 (80.0 KB) |
| Cヒープ空き(1スロット使用時、VDP+PSG+キャッシュ差引後) | 約15.5 KB | 約15.5 KB(据え置き) | 約15.5 KB(据え置き) |
| GCヒープへの影響 | — | 約8KB減 | 約16KB減(2ページ/ウィンドウ方式の約26.6KB減より軽い) |
| 両スロット同時ロード時の合計(§3の「既知のリスク」再計算) | 約80.5 KB(64KB予算超過) | 約96.5 KB(72KB予算超過) | 約112.5 KB(80KB予算をなお超過するが、2ページ/ウィンドウ方式の約128.5KBよりはるかに軽い) |

**追加で踏んだ罠と修正(victim×2導入直後の実機報告: Swap CartridgeでのメガロムロードがCヒープ枯渇なしに常に失敗)**: `cart_cache[]`のサイズはロードするROMの実サイズに関係なく常に固定(`(4+VICTIM_SLOTS)*8KB`)にもかかわらず、`msx_eject_cart()`が呼ばれるたびに無条件で`free()`し、`msx_load_cart_paged()`が直後に**同じサイズを即座に`malloc()`し直す**設計になっていた。これは`cart[]`側で既に一度踏んで`cart_alloc_cap[]`という再利用機構で対策済みだった「非圧縮Cヒープ上でN バイトを解放して直後に同じNバイトを要求しても、他の要因で断片化していれば失敗しうる」という教訓(本ドキュメント§3冒頭・`msx_core.h`のコメント参照)が、`cart_cache[]`では未対策のまま残っていたことが原因。victimプール追加でサイズが32KB→48KBに増えたことで、それまで運良く成立していたものが実際に破綻した。`msx_eject_cart()`は`cart_cache[]`を解放しないよう変更し(`cart[]`は従来通り解放)、`msx_load_cart_paged()`側で「既に確保済みならそのまま再利用、なければ新規`malloc()`」という判定に変更。小容量カートへの切替時(`msx_load_cart()`)は逆に`cart_cache[]`を明示的に解放し、不要な48KB常時確保を避けている。ネイティブホストビルドで、実際の呼び出し順序(`eject_cart()`を明示的に呼んでから`load_cart_paged()`を呼ぶ、Python側の実際のフローと同一)を再現し、ポインタが再利用されること・小容量カート切替時は正しく解放されることの両方をテストで確認済み。

victimスロット数を増やすたびにCヒープ・GCヒープへの影響も+8KBずつ比例して増える(RP2350版MicroPythonポートのリンカ制約でGCヒープは64KB超が必須——`memmap_mp_rp2350.ld`——なので、際限なく増やせるわけではない点に注意)。§4/§5/§6のGCヒープ関連の数値(約128.6KB等)は本更新の**前**の測定値のままなので、実機再ビルド後は`log_mem()`で新しい実測値を確認すること。

### 3.2 2026-10-11更新: `pico2_piousb`ビルド向けにCヒープを65536(64KB)へ個別縮小

pico2本体にもPIO-USBホスト対応(`bldfrm_msx.sh pico2_piousb`、GP4/GP5配線、空いたネイティブUSBをCDC REPL化)を追加した際、ベンダーしたpio_usbライブラリの静的状態(エンドポイントプール・root port構造体)とMicroPython本体のネイティブUSB CDCスタック(今回初めてpico2側でも有効化)の追加分で、`.bss`が通常版pico2比で約15.8KB増加した(実測、`__bss_end__`のリンクマップ比較)。

最初は「80KB→4KB減の77824」で試したが、リンク時の64KBフロアチェック(`memmap_mp_rp2350.ld`の`ASSERT`)は通過したものの、**実機で`msx_menu.py`コンパイル中に本当の`MemoryError`(1016バイト確保失敗)を実際に踏んだ**(§3.1の「victim×1(暫定)→victim×2」の経緯で既に一度踏んだのと同じ種類の誤り: リンク時フロアを満たすことと、実際のワークロードに十分な余裕があることは別問題)。

最終的に**65536(64KB)**へ戻して解決。これは偶然ではなく、victimプール導入前にこのプロジェクトが実際に使っていた値そのもの(`MSX_CART_VICTIM_SLOTS=0`、2026-10-08のメガロムキャッシュ断片化修正で両ボードとも`cart_cache[]`が再び32KBに戻っているため、この値がそのまま当てはまる)。結果、GCヒープは約80.5KB確保でき、通常版pico2(約78KB)よりやや多い余裕を確保している。

| 項目 | pico2 (ネイティブ) | pico2_piousb |
| :--- | ---: | ---: |
| `MICROPY_C_HEAP_SIZE` | 81920 (80KB) | 65536 (64KB) |
| `.bss`(概算差分) | 基準 | +約15.8KB(pio_usb + ネイティブUSB CDCスタック) |
| GCヒープ(実測) | 約79876バイト | 約80476バイト |

### 3.3 2026-10-17: victimスロット増量+Cヒープ拡大を試行 → 実機FPS悪化のため撤回

§8/§9のfrozen module化でGCヒープに余裕が生まれたことを受け、「Cヒープも少し余裕を持たせられないか」という提案から、`MSX_CART_VICTIM_SLOTS`を0→1→2、`MICROPY_C_HEAP_SIZE`をpico2(PIO-USB)で65536→73728、nativeusb/pizeroで81920→90112→94208まで段階的に引き上げる試みを行った(メガロムのバンク切替キャッシュヒット率を上げ、Swap Cartridgeでのメガロムロードも引き続き問題ないことを都度実機確認しながら進めた)。

しかし実機テストで**2つの独立した悪化**が判明し、最終的に全面撤回(`MSX_CART_VICTIM_SLOTS=0`、Cヒープは元の値へ)した:

1. **Cヒープ拡大そのものが、メガロムかどうかに関わらず全カートリッジでFPSを下げる**: victimプールを有効にしたままCヒープだけ元の65536に戻す切り分けビルドで検証したところ、非ページングの`ANTADV.ROM`が本来の約58〜59FPSを維持した(Cヒープを73728に増やした状態では約42〜43FPSまで低下していた)。Cヒープを増やす=GCヒープが同じだけ縮む(`MICROPY_C_HEAP_SIZE`は固定サイズの静的アリーナであり、同じ512KB SRAM予算をGC/Pythonヒープと奪い合う)ため、GCヒープが縮むことでMicroPythonの自動`gc.collect()`がより頻繁に走るようになったと推測される(メインループは`poll_keyboard()`の`report[2:8]`スライス等、カート種別に関わらず毎フレーム小さなPythonオブジェクトを確保している)。
2. **victimプール自体も、スロット数に関わらずNEMESIS.ROM(KONAMIマッパー)で悪化**: Cヒープを変更しない条件(victim×1のみ)でもNEMESIS.ROMは約45〜46FPSで頭打ちになり、victim×0の旧ベースラインで見られた「50台後半〜60近辺まで戻るバースト挙動」が消失した。victim×2に増やしてもバーストは戻らず(約46〜47FPS)、§3.1が記録した「共有スロット1つでは複数ウィンドウが競合する」という説明はこの回帰の真因ではなかったことが判明した——キャッシュヒット率の向上が、このタイトルでは実際のフレームレート向上に結びついていない。

**教訓**: `msx_get_cart_fetch_stats()`のキャッシュヒット率カウンタが改善しても、実機FPSが改善するとは限らない(キャッシュミス自体のコストより、victimプールのスキャン/スワップのオーバーヘッドの方が大きい場合がありうる)。また`MICROPY_C_HEAP_SIZE`の増量は、たとえ対象がメガロム専用の機能であっても**全カートリッジ・全操作に波及するFPSコスト**を伴いうるため、「GCヒープに名目上の余裕があるから」だけを理由にCヒープを増やす判断は避けるべきである。再挑戦する場合は、特定のタイトルで実際のFPS実測による効果確認が必須(キャッシュヒット率の改善だけでは不十分)。

## 4. GCヒープ(MicroPythonが管理するPythonオブジェクト領域)

**2026-08-17、`bldfrm_msx.sh`の実ビルドログから実測**(HDMIクリア機能追加後の最新ソースでのビルド):

```
Memory region         Used Size  Region Size  %age Used
             RAM:      327112 B       512 KB     62.39%
```

これはリンカが確定させる`.data`+`.bss`(静的領域)の合計であり、`msx_state_t`(§2, 計算値 約296.2KB)とMicroPythonランタイム自身の静的フットプリント(USBホストドライバのバッファ等を含む)の合計にあたる。逆算すると:

| 項目 | サイズ |
| :--- | ---: |
| リンカのRAM領域(ビルド設定上の上限) | 512.0 KB |
| 静的領域(`.data`+`.bss`)実測 | 319.4 KB (62.39%) |
| うち`msx_state_t`(§2の計算値) | 約296.2 KB |
| うちMicroPythonランタイム本体等その他の静的領域 | 約23.2 KB |
| Cヒープ(§3、`MICROPY_C_HEAP_SIZE`固定) | 64.0 KB |
| **残り(GCヒープ+スタック)** | **約128.6 KB (25.1%)** |

**設計方針**: 大きなデータ(RAM/VRAM/フレームバッファ)はPython側にコピーせず、C側メモリへの**ゼロコピー参照**(`bytearray_by_ref`)で済ませる方針を徹底している(`msx.get_ram_view()`/`get_vram_view()`/`get_framebuf()`)。MicroPythonのGCヒープは**非圧縮**のため、名目上の空き容量が十分でも大きな連続ブロックの確保は高確率で失敗する(`MemoryError`)——この教訓から、GCヒープには本来「数十〜数百バイト単位のPythonオブジェクト(モジュール名前空間、文字列、UI状態、セーブステートの64バイトヘッダ等)」しか乗らない設計になっている。

**注意**: 上記の約128.6KBは「GCヒープ+スタック」の合計であり、スタックが数KB程度差し引かれるため実際のGCヒープ(`gc.mem_free()`で見える値)はこれよりやや小さい。また過去(2026-08-01、`project_msx_emulator`メモリ参照)にダブルバッファ化直後の実機で`gc.mem_free()`を実測した際は約123KBだった(`disp_row_buf`を48KB→6KBに縮小した後の値)。今回のビルドログ由来の推定(~128.6KB)とほぼ整合しており、`msx_state_t`のレイアウトはその後大きく変わっていないことを裏付けている。**正確な実行時空き容量は実機で`gc.mem_free()`を実行して最終確認すること**(`doc/dev_guide.md`が新しい静的バッファ追加時の確認手順として推奨している)。

## 6. 拡張性の検証: PB-1000のようなサブルーチンフック機構の実現可能性

PB-1000エミュレータ(`src/hd61700.c`/`.h`、`src/modhd61700.c`)には、CAL(サブルーチン呼び出し)命令が登録済みアドレスをターゲットにした際、実際のサブルーチン実行の代わりにPythonコールバックを起動する「CALフック」機構(`hd61700.set_call_hook(address, callable)`)が実装されている。これと同等の仕組みをMSXエミュレータ(Z80コア)に実装した場合の、残ヒープ容量の観点での実現可能性を検証する。

### 6.1 PB-1000実装のメモリコスト実測

コードから直接計算した、この機構自体が消費する静的メモリ:

| 要素 | サイズ | 備考 |
| :--- | ---: | :--- |
| `call_hook_addrs[16]`(u16) | 32 B | フック登録アドレス一覧(`CALL_HOOK_MAX=16`) |
| `call_hook_fns[16]`(mp_obj_t、ポインタ) | 64 B | 登録されたPython callableへの参照(GCスキャン対象) |
| `call_hook_enabled[16]`(bool) | 16 B | 個別有効/無効フラグ |
| CPU構造体側(`call_hook`関数ポインタ+`cb_ctx`) | 8 B | |
| **合計(静的)** | **約120 B** | **無視できる規模** |

これに加え、登録されたPythonコールバック関数オブジェクト自体はGCヒープ上に確保されるが、MicroPythonの関数オブジェクトは数十〜100バイト程度であり、上限の16個すべて登録しても最大2KB未満。

### 6.2 結論: ヒープ容量の観点では実現可能性は非常に高い

§1〜5で整理した現状の余裕(Cヒープ約15.5KB、GCヒープ+スタック約128.6KB[2026-08-17ビルドログ実測])に対し、フック機構自体の追加コストは静的120B+GCヒープ数百B〜2KB程度と、いずれも**誤差の範囲に収まる**。ヒープ枯渇がボトルネックになる可能性は極めて低い。

ただし、これは「フック機構そのもの」のコストであり、**そのフックで実際に何をするか(用途側の実装)によっては別途メモリコストが発生する**点に注意。例えばPB-1000ではこの機構をFDD(フロッピーディスク)エミュレーションに応用しており(`fdd_protocol.py`/`fdd_storage.py`相当、現在は別プロジェクト管理)、仮想ディスクのバッファやプロトコル状態機械のためのメモリが別途必要になる。MSX側での具体的な用途(例: ディスクBASIC/BIOSコールの置き換え等)が定まっていないため、その部分の見積もりは用途確定後に別途行う必要がある。

### 6.3 参考: ヒープ以外の実現可能性の論点(本検証の範囲外だが記録)

- **Z80コア(`superzazu/z80`、サードパーティMITライブラリ)には現状この種のフック機構が存在しない**(`hd61700.c`のような`call_hook`フィールドがZ80の`struct z80`に無いことは確認済み、§本ドキュメント作成時に`z80.c`をgrepして確認)。追加するには、ライブラリ本体(`src/msx/z80/z80.c`)に手を入れるか、`msx_core.c`側でCALL/RST系命令の実行直前にPC比較を挟む形になる。
- **HD61700版は毎命令フェッチ前にPCをチェックする設計**(コメント曰く「BASICのCALLがpush+JPで実装されており間接CALLが無いCPUのため」)。Z80は真のCALL/RST命令を持つため、フック判定を「CALL/RSTニーモニックの分岐先アドレスチェックのみ」に限定すれば、命令フェッチのたびに走査するのではなくCALL/RST実行時のみのチェックで済み、HD61700版よりオーバーヘッドを抑えられる可能性がある。
- **性能面(ヒープではなくCPU時間/FPSの論点)**: フック未登録時はNULLチェック1回のみでほぼゼロコスト(PB-1000実装と同様の設計を踏襲すれば)。フック有効時は登録数分の線形走査(最大16件比較)が該当命令ごとに追加される。MSXのZ80(3.579545MHz)は命令実行数がPB-1000のHD61700より多いため、フック有効時のコストは無視できない可能性があるが、これはFPSへの影響であってヒープ容量とは独立の論点。

## 7. 参考: 関連する過去の教訓

- **`MICROPY_C_HEAP_SIZE`のデフォルトが0バイトである罠**: 未設定だとVDP/PSGの`malloc`/`calloc`がGCヒープ領域に静かに食い込み、原因不明のハングを起こす(`doc/build_guide.md`)。
- **GCヒープは非圧縮**: 名目上の空き容量が十分でも大きな連続ブロックの確保に失敗しうるため、大きなバッファは極力ゼロコピー参照にする(`doc/architecture.md`§セーブステート)。
- **静的バッファを増やす際は`gc.mem_free()`で実機確認**: ビルドログの「RAM: xxx / 512KB」は`.data`+`.bss`の静的使用量のみを示し、Cヒープ・GCヒープの余裕は別途実機で確認する必要がある(`doc/dev_guide.md`)。2026-09-08以降は`mp/msx_menu.py`の`log_mem()`ヘルパー(§4.1)で主要な節目の実測値がコンソールに出るので、これを使うのが最も手軽。
- **静的バッファはFPSが本当に必要な箇所だけに使う**: DMA投げっぱなし方式(フレーム全体を静的バッファに構築してから1回のDMA転送)はゲームプレイのFPS維持には有効だが、メニュー/UI画面のようにFPSを必要としない用途に同じ設計を持ち込むと、不要な静的バッファ(今回は49KB相当)を抱え込むことになる。同期的なブロッキング送信で十分な場面かどうかを先に見極める(§4.1)。

## 8. 2026-10-16〜17更新: `msx_menu.py`のUI層C化による定常的GCヒープ圧迫対策

### 8.1 背景・動機

§3.1/3.2/4.1で繰り返し踏んできた「Cヒープやその他の静的領域をわずかに増やしただけで、全く無関係な`.py`ファイルの遅延コンパイルが実機で`MemoryError`を起こす」というパターンの根本原因を再整理すると、ボトルネックは**GCヒープの絶対空き容量そのもの**というより、**非圧縮GCヒープ上で「ある程度まとまったサイズのPythonコードオブジェクトをその場でコンパイルする」という操作が、空き容量に対して要求するワーキングセットの大きさ**にあった。中でも`mp/msx_menu.py`は`msx_rom_browser.py`/`msx_runtime_menu.py`/`msx_save_slots.py`/`msx_display_settings.py`といった他のメニュー系モジュールと違い、`main.py`から**毎起動必ずeager import**される(遅延importされない)ため、その929行分のコンパイルコストは起動のたびに無条件で支払われていた。

これを受け、速度改善ではなく**定常的なヒープ逼迫の解消**を目的に、`msx_menu.py`の実装の大半を新設のCユーザーモジュール`msx_ui`(`src/modmsx_ui.c`)へ段階的に移植した。C側の関数・定数は`.bss`/`.text`(リンカが確定する静的領域、フラッシュ上の`.text`含む)にコンパイルされ、**MicroPythonのバイトコードコンパイラにも、GCヒープ上のコードオブジェクトにもならない**ため、このアプローチは「起動のたびに毎回支払うコンパイルコスト」そのものをゼロにできる。

### 8.2 実施内容(3フェーズ)

| フェーズ | 内容 | `msx_menu.py`の行数 |
| :--- | :--- | ---: |
| (着手前) | — | 929行 |
| フェーズ1 | `MenuCanvas`描画コア(`framebuf`非経由、`msx_core.c`と同じRGB565バイトスワップを直接実装)・色/HID定数・表示サスペンド状態・USBキーボードポーリング(`usb_host_core_task()`等への直接Cコール)・メッセージ表示 | 643行 |

**意図的にC化しなかった部分**: `msx.load_cart_paged()`(メガロムのバンク切替フェッチにおける、Pythonファイルオブジェクトのchange GCルート保持を伴う複雑な状態機械、§3参照)自体は再実装せず、`msx_ui`からは`mp_load_method`/`mp_call_method_n_kw`ベースの汎用メソッド呼び出しヘルパー経由で既存の`modmsx.c`実装にそのまま委譲している。これは本対策の対象(定常的なコンパイルコスト)ではなく、実機実績のある複雑な機構を目的と無関係に再実装するリスクを避けるための意図的な判断。

**呼び出し側への影響ゼロ**: `main.py`/`msx_rom_browser.py`/`msx_runtime_menu.py`等、`msx_menu.py`以外の`.py`ファイルは3フェーズ通じて一切変更していない。`msx_menu.py`は`from msx_ui import (... as _xxx, ...)`で全ての名前を元のPython名のまま再公開しているだけで、呼び出し規約は変わっていない。サブルーチン(CALL/RST)フック機構はこのC化と無関係で、引き続きPython専用(`msx.set_call_hook()`)のまま。

### 8.3 静的領域への影響

### 8.4 教訓

- **「速度改善」と「ヒープ逼迫解消」は別の目的であり、C化のアプローチも変わる**: 単純に全体をC化するなら呼び出し規約自体を再設計する余地もあったが、今回の目的はGCヒープのコンパイルコスト削減のみだったため、**既存のPython呼び出し規約を一切変えずに実装だけをCへ移す**(`msx_menu.py`を透過的な再公開レイヤーに変える)方針を徹底した。これにより、他の`.py`ファイルのレビュー・実機再テストが一切不要になった。
- **「常にeager importされるモジュールほど優先度が高い」という優先順位づけ**: `msx_rom_browser.py`等の遅延importされるモジュールはそもそも使われるまでコンパイルコストを払わないため、このC化の対象として急ぐ必要がない。eager importされる`msx_menu.py`(および`main.py`自身)こそが定常的な圧迫の実体だった。
- **非string値を見落とさないための事前grep**: `save_config()`の呼び出し元を網羅的にgrepしたところ、大半は文字列化済みの値を渡していたが`msx_runtime_menu.py`の音量/フィルタ保存だけは整数を直接渡していることが判明。実装前に全呼び出し元を洗い出す習慣が、型を決め打ちした実装によるバグを未然に防いだ(詳細は`src/modmsx_ui.c`の`ui_save_config()`コメント参照)。
- **ビルドツールの並行実行には要注意**: `bldfrm_msx.sh`は共有の中間ソースコピーディレクトリを使うため、複数バリアントを同時にバックグラウンドビルドすると一方の`cp`がもう一方のソースを破壊し、無関係な箇所のリンクエラーという紛らわしい形で現れることがある(詳細は`bldfrm_msx.sh`自身のコメント/コミット履歴参照)。複数バリアントのビルドは必ず逐次実行すること。

## 9. 2026-10-17: frozen module化によるさらなるヒープ確保(pico2/pico2_piousb)

> §9.1〜9.6: 1ファイル(`board_config.py`)でのトライアル、実機確認済み。
> §9.7以降: `main.py`分割+計12ファイルへの大幅拡大。起動時のヒープ実測(pico2ネイティブUSBホスト版)は確認済み(+30,240B@boot、§9.7参照)、**PIO-USB版やメニュー画面の網羅的な動作確認、接続安定性の再確認は引き続き未実施**。

### 9.1 背景

§8でC化した`msx_menu.py`以外にも、`main.py`からeager importされ常時コンパイルコストを払っているモジュールは複数残っている(`board_config.py` 261行、`msx_keymap.py` 250行、`msx_ext.py` 82行)。これらをC化する前段として、**より工数の少ない代替手段**としてMicroPythonのfrozen module機構(`FROZEN_MANIFEST`、ビルド時に対象`.py`をバイトコード化してファームウェアのflashへ直接焼き込み、GCヒープ上のコンパイルコストを完全にゼロにする仕組み)を試すことにした。

### 9.2 ⚠️ 重要な前例: 2026-09-30、pizeroで一度試して撤回済み

`src/msx/boards/WAVESHARE_RP2350_PIZERO/mpconfigboard.cmake`に記録が残っている通り、**このプロジェクトは以前に一度、遅延importされるメニュー系モジュールのfreezeをpizeroで試し、実機で「`mpremote`/UART接続が断続的に失敗する(`No such device`)」という原因不明の不具合が再現したため撤回している**(2種類の異なるUSBシリアルアダプタ・電源入れ直しでも再現確認済み、根本原因は未特定のまま)。

2026-10-17時点でユーザーから「当時はpizeroのREPLがGP0/1のUART経由だったが、現在はpizero/pico2_piousbともネイティブUSB CDC REPLに切り替わっているため、当時の懸念は薄いのではないか」との指摘があった。これは合理的な仮説だが、**根本原因を特定しないまま撤回した事象であるため、REPLのトランスポートが変わったことで本当に解消したのかは実機で確かめるまで分からない**(plain pico2は現在もUART REPLのままであり、そもそもpico2でfreeze自体を試した実績が一度もない)。

この仮説を直接検証するため、ユーザーから「UART REPLのpico2(ネイティブUSBでキーボード接続)とCDC REPLのpico2_piousb(PIO-USBでキーボード接続)の両方をビルドし、安定性を比較したい」との要望があり、トライアル対象を**pico2_piousbにも拡大**した(pizeroは引き続き対象外)。

### 9.3 今回の方針: pico2/pico2_piousb・1ファイルのみでの慎重なトライアル

上記を踏まえ、次の手順で慎重に進めることにした:

1. **pico2とpico2_piousbのみ**でfreezeを有効化(`src/msx/micropython_msx.cmake`で`NOT MSX_IS_PIZERO`のときだけ`MICROPY_FROZEN_MANIFEST`を差し替え)。pizero向けの設定は一切変更していない。
2. **対象ファイルは`board_config.py`1つだけ**(純粋な定数定義のみでロジックがほぼ無く、3候補の中で最もリスクが低いと判断)。`msx_keymap.py`/`msx_ext.py`は今回は対象外。
3. `src/msx/manifest_freeze.py`(新規)で`include("$(PORT_DIR)/boards/manifest.py")`により既存のデフォルト設定(asyncio/onewire/ds18x20/dht/neopixel、本プロジェクトは未使用だが維持)を保持しつつ、`freeze("$(MSX_MP_DIR)", "board_config.py")`を追加。
4. `bldfrm_msx.sh`は`mp/`をビルド時のみ`${DST_DIR}/mp`へローカルコピーする工程を追加(freeze処理がGoogle Driveマウント越しに読むのを避けるため、`src/`コピーと同じ理由)。**デバイスへの実際のデプロイ方法(`mpremote cp`)はこれにより一切変更していない**。

### 9.5 実機検証結果(2026-10-17、pico2/pico2_piousb両方)

**両ファームウェアとも問題なし**。`mpremote connect /dev/ttyUSB0 ls`でのファイル一覧確認により、**`board_config.py`がデバイスのファイルシステム上に存在しない状態で正常動作していることを実証**(frozen版が実際に使われていることの直接的な証拠——ファイルシステム上に無い以上、動作している`board_config`モジュールはfrozen版以外あり得ない)。§9.2で挙げた「`mpremote`/接続の断続的切断」症状も、UART REPL(pico2)・CDC REPL(pico2_piousb)のいずれでも再現しなかった。

これにより:
- 今回の1ファイル(`board_config.py`)・2ボード(pico2/pico2_piousb)構成でのfreezeは実機で安全性を確認できた
- §9.2のユーザー仮説(2026-09-30のpizero不具合はUART REPL固有だったのでは)について、少なくとも「CDC REPL(pico2_piousb)でも、UART REPL(pico2)でも、freeze自体は問題を起こさない」ことは確認できた。ただし、pizero固有のハードウェアレイアウト逼迫(§9.2参照)が原因だった可能性は依然残っており、pizero自身での検証を経ない限り「pizeroでも安全」とは言い切れない。

### 9.7 2026-10-17: ユーザー指示により大幅拡大(main.py分割+計12ファイル、実機未検証)

§9.5の実機確認を受け、ユーザーから「フリーズ対象のpyファイルをもっと増やし、可能な限りヒープを確保する方向に進めてほしい」との明示的な指示があった。これに応じ、**`main.py`/`boot.py`以外の全`.py`ファイルをfreeze対象に拡大**した:

- 追加: `msx_keymap.py`・`msx_ext.py`・`msx_menu.py`・`sdcard.py`・`msx_mode_switch.py`・`msx_fdd.py`・`msx_rom_browser.py`・`msx_runtime_menu.py`・`msx_save_slots.py`・`msx_display_settings.py`(計10ファイル、`board_config.py`と合わせて11ファイル)
- 全ファイル、モジュールレベルでの副作用(import時に実行される関数呼び出し等)が無いこと、`__file__`等frozen moduleが提供できない機能に依存していないことを事前にgrepで確認済み。

**さらに`main.py`自体(1353行、このプロジェクト最大の常時eager importファイル)もfreeze対象に加えるため、新規に`mp/msx_app.py`を作成し、`main.py`の実体(起動フロー・メインループの全ロジック)をそちらへそのまま移動した**。`main.py`自体は以下のような薄いランチャーに縮小:

```python
from msx_app import run

if __name__ == '__main__':
    run()
```

`main.py`は自動起動のエントリポイント(MicroPythonの起動シーケンスが直接execする実ファイル)であるためfreeze不可——frozen moduleは通常の`import`機構経由でしか到達できず、トップレベルスクリプトとして自動実行される対象にはなれない。そのため`main.py`自体は今後もeager importのコストを払い続けるが、その中身は「`from msx_app import run`」1行だけなので、コストはほぼゼロになる。`doc/build_guide.md`/`usage_guide.md`に記載された開発時のREPLショートカット`import main; main.run()`は、`main.run`が`msx_app.run`の再公開のため変更なく動作する(§8の`msx_menu.py`→`msx_ui`再公開と同じパターン)。

**最終的なfreeze対象は計12ファイル**: `board_config.py`・`msx_keymap.py`・`msx_ext.py`・`msx_menu.py`・`sdcard.py`・`msx_mode_switch.py`・`msx_fdd.py`・`msx_rom_browser.py`・`msx_runtime_menu.py`・`msx_save_slots.py`・`msx_display_settings.py`・`msx_app.py`。

両ボードともRAMは完全に不変(想定通り)。ビルドログで全12ファイルの`MPY`出力(`msx_app.py`含む)を確認済み。

**実機検証(2026-10-17、pico2ネイティブUSBホスト版のみ)**: `mpremote run mp/main.py`での起動ログを実測。同一実機・同一BIOS/カートリッジ(`MSX_jp.rom`+`ANTADV.ROM`)で§8.3と同じ3地点を比較した:

| 計測タイミング | フェーズ3のみ(C化、freeze無し) | 今回(C化+12ファイルfreeze) | 今回の差分 | 累計差分(§8着手前比) |
| :--- | ---: | ---: | ---: | ---: |
| `boot, after main.py/msx_menu.py compiled` | 41,120 B | 71,360 B | **+30,240 B** | +38,400 B |
| `after BIOS load` | 50,240 B | 68,512 B | +18,272 B | +26,032 B |
| `after cart load` | 49,632 B | 67,936 B | +18,304 B | +26,160 B |

正常起動・BIOS/カートロード・60FPS前後の動作いずれも問題なし。

**観測された興味深い変化(「山」が消えた)**: freeze無しの場合、boot→BIOS後にかけて空き容量が**増えていた**(41,120→50,240、+9.1KB)——これは`_load_bios()`内の`gc.collect()`が、直前に`main.py`/`msx_menu.py`自体をコンパイルした際の一時的なパースツリー等のゴミを回収していたため(非圧縮GCヒープが一時的に断片化し、その後の`gc.collect()`で回収されるという典型パターン)。今回(12ファイルfreeze後)は同じ区間で**減っている**(71,360→68,512、-2.8KB、configパース等の通常の小さな確保によるもの)。これは、freezeによって「回収すべきコンパイル時のゴミ」自体がそもそも発生しなくなったことを裏付けている——以前の`gc.collect()`の「ボーナス」は、eager importされるコードが定常的に生み出していたゴミの副産物だった。

これにより、**起動時点での実測+30,240B、定常状態(カートロード後)での実測+18,304B**というfreeze単体の効果と、**着手前(§8着手前、929行版`msx_menu.py`+freeze無し)からの累計で+26,160B(定常状態)**という本プロジェクト全体での改善量が、いずれも実測で確認された。

**2026-10-17追記: PIO-USB版でも実機確認済み**。ネイティブUSBホスト版に続き、PIO-USB版(新命名`pico2`/`firmware_msx.uf2`、デフォルト)でも12ファイルfreeze+`main.py`/`msx_app.py`分割構成で正常動作を確認。これにより§9.2のユーザー仮説(2026-09-30のpizero不具合がUART REPL固有だったのでは)について、少なくとも「pico2系列(ネイティブUSB/PIO-USBいずれのREPLトランスポートでも)freeze自体が問題を起こさない」ことが、今回の拡大構成(12ファイル)でも裏付けられた。pizero自身は引き続き未検証(§9.2参照)。

### 9.8 教訓(現時点、確定ではなく進行中の記録)

- **过去の失敗は「原因不明のまま撤回」だったため、「似た条件がなくなったから大丈夫」という推測だけで前へ進めるべきではない**: ユーザー指摘のREPLトランスポートの変化は有力な仮説だが、plain pico2は当時と同じUART REPLのままであり、そもそもpico2での実績が無い以上、新規の実機検証と同等に慎重に扱う。
- **1ファイル・2ボードまで刻んだ上で、仮説検証になるよう意図的に組み合わせを選ぶ**: pizeroを除外しつつpico2_piousbを加えたのは、単にリスクを均等に避けるためではなく、「UART REPL(pico2) vs CDC REPL(pico2_piousb)」という条件の違いを意図的に作ることで、§9.2の仮説(REPLトランスポートが原因かどうか)を実機データで直接比較できるようにするため。
