# メモリ使用量の内訳

Raspberry Pi Pico 2 (RP2350、リンカ上のRAM領域512KB、物理SRAM総量520KB) 上でMSX1エミュレータが何にどれだけメモリを使っているかを整理する。`msx_state_t`(§2)の内訳はソースコード(`src/msx/msx_core.h`/`.c`、`src/msx/tms9918/`、`src/msx/emu2149/`)から構造体サイズを直接計算した値(`sizeof()`を実機で出力して検証したものではなく、パディングにより数〜数十バイト程度前後する可能性がある)。静的領域合計(§4)は2026-08-17に実際にビルドしたログの実測値。GCヒープ単体の実測空き容量は§4末尾を参照。

## 1. 全体像

リンカのRAM領域(512KB)は、大きく3つの領域に分かれる。

| 領域 | サイズ | 内容 | 管理者 |
| :--- | ---: | :--- | :--- |
| 静的領域(`.data`+`.bss`) | 319.4KB(実測) | `msx_state_t`(約296.2KB、計算値)+MicroPythonランタイム本体等(約23.2KB) | リンカ(コンパイル時に確定) |
| Cヒープ | 64KB(固定、`MICROPY_C_HEAP_SIZE=65536`) | VDPコア・PSGコア・カートリッジROM | `malloc()`/`calloc()` |
| GCヒープ + スタック | 残り 約128.6KB(実測) | Pythonオブジェクト全般 | MicroPython GC |

```
512KB RAM(リンカ領域)
├─ 静的領域 (.data+.bss)        319.4KB (62%)  ← うちmsx_state_tが296.2KB(ダブルバッファ化されたフレームバッファが主因)
├─ Cヒープ (malloc/calloc)       64.0KB (12%)  ← VDP+PSG+カートリッジROM
└─ 残り(GCヒープ+スタック)       128.6KB (25%)
```

**最大の消費源は`msx_state_t`という1つのグローバル構造体**であり、Cヒープでもなく、そもそもMicroPythonのGCヒープでもない。この構造体はコンパイル時にサイズが固定される(`.bss`セクション)ため、実行時のメモリ確保失敗(`MemoryError`)には直接関与しないが、リンカのRAM領域(512KB)の過半数を最初から占有している。

---

## 2. 静的領域(`.bss`): `msx_state_t` の内訳

`src/msx/msx_core.h` で定義されているグローバル構造体1個(`msx_state`)がプログラム全体で唯一のインスタンス。

| フィールド | サイズ | 用途 |
| :--- | ---: | :--- |
| `framebuf[2][256×192]` (u16) | **192.0 KB** | 表示用フレームバッファ(ダブルバッファ)。**最大の単一消費項目** |
| `ram[0x10000]` | 64.0 KB | MSXスロット3(メインRAM) |
| `bios[0x8000]` | 32.0 KB | MSXスロット0(BIOS/BASIC ROM) |
| `disp_row_buf[2][4×384]` (u16) | 6.0 KB | 1.5倍拡大表示用ステージングバッファ(現状の本番描画パスでは未使用、拡張用に残置) |
| `audio_buf[512]` (i16) | 1.0 KB | PSGオーディオのリングバッファ |
| `scanline_buf[256]` | 0.25 KB | 1スキャンライン分の作業バッファ |
| `disp_col_src[384]` (u16) | 0.75 KB | 拡大表示用の列マッピングテーブル |
| `key_matrix[11]` ほか小フィールド多数 | 約0.1 KB | キーボード行列・スロット選択・SPI/HDMI設定・ジョイスティック状態など |
| `z80 cpu`(CPUコア本体) | 約0.07 KB | レジスタ・フラグ一式(無視できる規模) |
| `vdp`/`psg` ポインタ | 8 B | Cヒープ上のVDP/PSGインスタンスへのポインタ(実体は§3) |
| **合計** | **約296.2 KB** | |

**内訳の要点:**
- **`framebuf`のダブルバッファ化(192KB)が支配的**。表示DMA転送とZ80/VDPエミュレーションを並行実行するパイプライン設計のトレードオフとして、シングルバッファ(96KB)の2倍を消費している(2026-08-01のFPS改善作業で採用、詳細は`project_msx_emulator`メモリ参照)。
- `disp_row_buf`は元々1.5倍拡大表示(ST7796パネル用)のために32バッチ分(48KB)確保されていたが、GCヒープ圧迫が発覚し4バッチ分(6KB)に縮小済み。現在の本番描画は等倍パス(`render_to_display_1to1()`)を使うためこのバッファ自体使われていないが、将来の拡大表示再有効化に備えて残置されている。
- `bios`(32KB)+`ram`(64KB)の96KBはMSXのメモリマップそのものであり、これ以上削れない。

## 3. Cヒープ(`malloc`/`calloc`、64KB固定)

MicroPython RP2ポートはCの`malloc()`/`calloc()`用ヒープをデフォルト0バイトとするため、`bldfrm_msx.sh`が`MICROPY_C_HEAP_SIZE=65536`(64KB)を明示的に指定している。これを怠るとVDP/PSGの`malloc`がGCヒープ領域を静かに破壊し原因不明のハングを起こす(実際に踏んだバグ、`doc/build_guide.md`参照)。

| 消費者 | サイズ | 確保タイミング |
| :--- | ---: | :--- |
| VDPコア(`VrEmuTms9918`、`vram[16384]`が主体) | 約16.3 KB | `msx_init()`時に1回、以後解放されない |
| PSGコア(`PSG`構造体) | 約0.15 KB | `msx_init()`時に1回 |
| カートリッジROM | 最大 **32 KB** / スロット | ROM選択時(下記2モードのいずれか) |
| **常時消費**(VDP+PSG) | **約16.5 KB** | |
| **カートリッジ込みの実質使用**(1スロット時) | **約48.5 KB** | 64KB予算のうち残り約15.5KBが余裕 |

カートリッジROMの確保は`load_cart_smart()`がサイズに応じて自動選択する2モードだが、**どちらのモードでも最終的に64KB C ヒープを消費する**点は同じ:

- **フルRAMロード**(`msx_load_cart()`、非バンク切替・32KB以下向け): ROM全体を一度に`malloc()`。
- **メガロムページング**(`msx_load_cart_paged()`、128KB以上のバンク切替カート向け): 現在選択中の4バンク×8KB=**32KB固定**のキャッシュのみ保持(ROM実サイズに関係なく常に32KB)。実データはPico2内蔵フラッシュの`/megarom_cache.rom`から都度フェッチする。

いずれの場合もカートリッジ1本あたり32KBが上限となるよう設計されているため、VDP(16.3KB)+PSG(0.15KB)+カート(32KB)=約48.5KBで収まり、64KB予算に約15.5KBの余裕がある。

**⚠️ 既知のリスク**: カートリッジスロットは2つ(`cart[2]`/`cart_cache[2]`)存在し、**両スロットに同時にROMをロードした場合、単純計算で32KB×2=64KBとなりVDP/PSG分を合わせて約80.5KBとなって64KB予算を超過する**。マルチスロットカートリッジ(スロット2)は`project_msx_emulator`メモリの残タスクにある通り実機未検証であり、この構成でのメモリ超過リスクは未確認。実機検証時は`gc.mem_free()`だけでなくCヒープ枯渇によるハング(GCヒープ破壊と同じ症状)にも注意が必要。

## 4. GCヒープ(MicroPythonが管理するPythonオブジェクト領域)

**2026-08-17、`bldfrm_msx.sh`の実ビルドログから実測**(HDMIクリア機能追加後の最新ソースでのビルド):

```
Memory region         Used Size  Region Size  %age Used
             RAM:      327112 B       512 KB     62.39%
```

これはリンカが確定させる`.data`+`.bss`(静的領域)の合計であり、`msx_state_t`(§2, 計算値 約296.2KB)とMicroPythonランタイム自身の静的フットプリント(USBホストドライバのバッファ等を含む)の合計にあたる。逆算すると:

| 項目 | サイズ |
| :--- | ---: |
| リンカのRAM領域(ビルド設定上の上限) | 512.0 KB |
| 静的領域(`.data`+`.bss`)実測 | 319.4 KB (62.39%) |
| うち`msx_state_t`(§2の計算値) | 約296.2 KB |
| うちMicroPythonランタイム本体等その他の静的領域 | 約23.2 KB |
| Cヒープ(§3、`MICROPY_C_HEAP_SIZE`固定) | 64.0 KB |
| **残り(GCヒープ+スタック)** | **約128.6 KB (25.1%)** |

**設計方針**: 大きなデータ(RAM/VRAM/フレームバッファ)はPython側にコピーせず、C側メモリへの**ゼロコピー参照**(`bytearray_by_ref`)で済ませる方針を徹底している(`msx.get_ram_view()`/`get_vram_view()`/`get_framebuf()`)。MicroPythonのGCヒープは**非圧縮**のため、名目上の空き容量が十分でも大きな連続ブロックの確保は高確率で失敗する(`MemoryError`)——この教訓から、GCヒープには本来「数十〜数百バイト単位のPythonオブジェクト(モジュール名前空間、文字列、UI状態、セーブステートの64バイトヘッダ等)」しか乗らない設計になっている。

**注意**: 上記の約128.6KBは「GCヒープ+スタック」の合計であり、スタックが数KB程度差し引かれるため実際のGCヒープ(`gc.mem_free()`で見える値)はこれよりやや小さい。また過去(2026-08-01、`project_msx_emulator`メモリ参照)にダブルバッファ化直後の実機で`gc.mem_free()`を実測した際は約123KBだった(`disp_row_buf`を48KB→6KBに縮小した後の値)。今回のビルドログ由来の推定(~128.6KB)とほぼ整合しており、`msx_state_t`のレイアウトはその後大きく変わっていないことを裏付けている。**正確な実行時空き容量は実機で`gc.mem_free()`を実行して最終確認すること**(`doc/dev_guide.md`が新しい静的バッファ追加時の確認手順として推奨している)。

## 5. まとめ表

| 領域 | サイズ | 全体(512KB)に占める割合 |
| :--- | ---: | ---: |
| `framebuf`(ダブルバッファ) | 192.0 KB | 37.5% |
| `ram`(MSXメインRAM) | 64.0 KB | 12.5% |
| Cヒープ(VDP+PSG+カート、フル使用時) | 64.0 KB | 12.5% |
| `bios`(BIOS/BASIC ROM) | 32.0 KB | 6.3% |
| `disp_row_buf`ほかmsx_state_t残り+MicroPythonランタイム本体等 | 31.4 KB | 6.1% |
| **GCヒープ+スタック**(残り、実測値は§4参照) | **約128.6 KB** | **25.1%** |

(リンカの「RAM」領域は512KBで、RP2350の物理SRAM総量520KBよりやや小さい——ビルド設定上、境界の一部が予約されているため。以降の割合は512KB基準。)

## 6. 拡張性の検証: PB-1000のようなサブルーチンフック機構の実現可能性

PB-1000エミュレータ(`src/hd61700.c`/`.h`、`src/modhd61700.c`)には、CAL(サブルーチン呼び出し)命令が登録済みアドレスをターゲットにした際、実際のサブルーチン実行の代わりにPythonコールバックを起動する「CALフック」機構(`hd61700.set_call_hook(address, callable)`)が実装されている。これと同等の仕組みをMSXエミュレータ(Z80コア)に実装した場合の、残ヒープ容量の観点での実現可能性を検証する。

### 6.1 PB-1000実装のメモリコスト実測

コードから直接計算した、この機構自体が消費する静的メモリ:

| 要素 | サイズ | 備考 |
| :--- | ---: | :--- |
| `call_hook_addrs[16]`(u16) | 32 B | フック登録アドレス一覧(`CALL_HOOK_MAX=16`) |
| `call_hook_fns[16]`(mp_obj_t、ポインタ) | 64 B | 登録されたPython callableへの参照(GCスキャン対象) |
| `call_hook_enabled[16]`(bool) | 16 B | 個別有効/無効フラグ |
| CPU構造体側(`call_hook`関数ポインタ+`cb_ctx`) | 8 B | |
| **合計(静的)** | **約120 B** | **無視できる規模** |

これに加え、登録されたPythonコールバック関数オブジェクト自体はGCヒープ上に確保されるが、MicroPythonの関数オブジェクトは数十〜100バイト程度であり、上限の16個すべて登録しても最大2KB未満。

### 6.2 結論: ヒープ容量の観点では実現可能性は非常に高い

§1〜5で整理した現状の余裕(Cヒープ約15.5KB、GCヒープ+スタック約128.6KB[2026-08-17ビルドログ実測])に対し、フック機構自体の追加コストは静的120B+GCヒープ数百B〜2KB程度と、いずれも**誤差の範囲に収まる**。ヒープ枯渇がボトルネックになる可能性は極めて低い。

ただし、これは「フック機構そのもの」のコストであり、**そのフックで実際に何をするか(用途側の実装)によっては別途メモリコストが発生する**点に注意。例えばPB-1000ではこの機構をFDD(フロッピーディスク)エミュレーションに応用しており(`fdd_protocol.py`/`fdd_storage.py`相当、現在は別プロジェクト管理)、仮想ディスクのバッファやプロトコル状態機械のためのメモリが別途必要になる。MSX側での具体的な用途(例: ディスクBASIC/BIOSコールの置き換え等)が定まっていないため、その部分の見積もりは用途確定後に別途行う必要がある。

### 6.3 参考: ヒープ以外の実現可能性の論点(本検証の範囲外だが記録)

- **Z80コア(`superzazu/z80`、サードパーティMITライブラリ)には現状この種のフック機構が存在しない**(`hd61700.c`のような`call_hook`フィールドがZ80の`struct z80`に無いことは確認済み、§本ドキュメント作成時に`z80.c`をgrepして確認)。追加するには、ライブラリ本体(`src/msx/z80/z80.c`)に手を入れるか、`msx_core.c`側でCALL/RST系命令の実行直前にPC比較を挟む形になる。
- **HD61700版は毎命令フェッチ前にPCをチェックする設計**(コメント曰く「BASICのCALLがpush+JPで実装されており間接CALLが無いCPUのため」)。Z80は真のCALL/RST命令を持つため、フック判定を「CALL/RSTニーモニックの分岐先アドレスチェックのみ」に限定すれば、命令フェッチのたびに走査するのではなくCALL/RST実行時のみのチェックで済み、HD61700版よりオーバーヘッドを抑えられる可能性がある。
- **性能面(ヒープではなくCPU時間/FPSの論点)**: フック未登録時はNULLチェック1回のみでほぼゼロコスト(PB-1000実装と同様の設計を踏襲すれば)。フック有効時は登録数分の線形走査(最大16件比較)が該当命令ごとに追加される。MSXのZ80(3.579545MHz)は命令実行数がPB-1000のHD61700より多いため、フック有効時のコストは無視できない可能性があるが、これはFPSへの影響であってヒープ容量とは独立の論点。

## 7. 参考: 関連する過去の教訓

- **`MICROPY_C_HEAP_SIZE`のデフォルトが0バイトである罠**: 未設定だとVDP/PSGの`malloc`/`calloc`がGCヒープ領域に静かに食い込み、原因不明のハングを起こす(`doc/build_guide.md`)。
- **GCヒープは非圧縮**: 名目上の空き容量が十分でも大きな連続ブロックの確保に失敗しうるため、大きなバッファは極力ゼロコピー参照にする(`doc/architecture.md`§セーブステート)。
- **静的バッファを増やす際は`gc.mem_free()`で実機確認**: ビルドログの「RAM: xxx / 512KB」は`.data`+`.bss`の静的使用量のみを示し、Cヒープ・GCヒープの余裕は別途実機で確認する必要がある(`doc/dev_guide.md`)。
