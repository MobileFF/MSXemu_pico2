# Changelog

All notable changes to this project are documented in this file. Japanese version: [CHANGELOG_ja.md](CHANGELOG_ja.md).

## [Unreleased]

### Added

- **Z80 CALL/RST hook extension mechanism**: drop a module in `/sd/msx/ext/` or the onboard flash's `/ext/` and it's auto-loaded at boot (`mp/msx_ext.py`), no `main.py` edits required. Same design as the sibling PB-1000 emulator's loader.
- Debug helper APIs rounding out the hook mechanism: `msx.debug_set_cpu()` (write-back counterpart to `msx.debug_cpu()`, which now also returns `bc`/`de`/`hl`/`ix`/`iy`), `msx.debug_poke()`, and `msx.debug_get_slot()`/`msx.debug_set_slot()`. See `doc/extension_api.md` / `doc/extension_api_en.md`.
- Documented a real hardware-tested caveat: hooking an interrupt vector (e.g. `0x0038`) permanently disables interrupts, since the hook mechanism skips the handler's own `EI` along with everything else it replaces.

### Fixed

- **Runtime menu (GUI+F7) crash on real hardware** (`OSError: [Errno 5] EIO`): the main loop starts a frame's LCD DMA transfer and polls the keyboard while it's still in flight (deliberate pipelining for speed). If the menu hotkey landed in that window, the menu's own first draw would reconfigure and restart the same DMA channel/SPI peripheral without ever waiting for the previous transfer to finish — a race independent of the HDMI bridge, which earlier investigation had focused on. Fixed by draining any in-flight transfer (`msx.wait_display()`) before the menu can touch the shared SPI1 bus.
- **Cartridge-swap failures** (`cart_alloc() failed`) exposed once the crash above was fixed: `MICROPY_C_HEAP_SIZE`'s non-compacting allocator couldn't satisfy a 32KB allocation after freeing a smaller cart's block, even with nominal free space available elsewhere on the heap. `msx_cart_alloc()` now reuses one capacity-tracked buffer across cart swaps on the same slot instead of `free()`ing and `malloc()`ing on every load — no extra RAM budget needed (a bigger C heap, or a static buffer, was tried first and both shrank the separate MicroPython GC heap by the same amount, breaking boot-time module imports instead).
- **`config.txt` read failures silently falling back to defaults**: a transient SD read error while opening `config.txt` was indistinguishable from "no config file exists," producing a confusing "BIOS not found" error even when `bios=` was set correctly. `load_config()` now retries a few times and logs a warning if it still can't read the file.
- **SD read/write speed accidentally pinned at 400kHz**: the SD card driver's per-transfer baud rate was reusing the constant meant only for the initial low-speed handshake, so every block read/write ran at 400kHz regardless of the configured LCD/SPI speed. Split into a separate `SD_DATA_BAUD` (4MHz) — both a reliability and a throughput fix.
- **Menu crashes ending the game session**: the runtime menu now catches an unexpected exception, logs the full traceback to `/crashlog.txt` on internal flash (not SD — logging to the card that just failed would be circular), attempts to reinitialize the LCD if it was left frozen, and resumes gameplay instead of crashing the whole `main.py` loop.
- Menu status/error messages (e.g. a full `OSError` message) are now also printed to the serial console — the LCD's 31-character line was silently truncating them.

### Added (2026-09-04/05)

- **HDMI Display Settings menu (GUI+F7)**: LCD panel model, rotation, HDMI baud rate, and a new `boot_exclusive` option, editable from the runtime menu alongside the existing Audio/HDMI Settings screens. All four are restart-only (read once at boot by `msx.init_display_hardware()`/`msx.init_hdmi_output()`) — the screen says so, and ENTER writes them to `msx.ini` without applying them live.
- **`boot_exclusive` config option**: combined with `display=lcd` or `display=hdmi` (not `both`), skips the unused side's hardware initialization entirely at boot — `display=hdmi` skips the LCD panel reset/init sequence outright (real boot-time saving, and the LCD need not be physically present); `display=lcd` skips `msx.init_hdmi_output()` even if `hdmi=1`. Either can still be turned on live from the menu afterward.
- **ROM selector folder navigation**: `select_rom()` now browses from the SD card root (was hardcoded to `/sd/msx`) and can navigate into subfolders — UP/DOWN move, ENTER opens a folder or picks a `.ROM`, ESC goes up a level (or cancels at the root). Falls back to a recursive first-match search when there's no keyboard attached.
- **HDMI send is now DMA-driven** (`msx_render_to_hdmi()`): the whole frame is built into a static buffer, then sent as a single DMA transfer left in-flight (same pattern already used by the LCD path), instead of 192 separate blocking `spi_write_blocking()` calls. Real-hardware FPS with `hdmi=1` improved substantially over the old fully-blocking send (~40ms/frame at 10MHz).
- **hdmi_bridge_receiver**: the top-left reception-confirmation marker is now hidden (painted black) during actual gameplay frames and only shown for menu/UI screens (ROM selector, runtime menu) — uses the existing per-frame `bpp` header field (4=game, 8=menu) already sent by the sender, no protocol change needed.

### Changed (2026-09-04/05)

- **Config file renamed and relocated**: `/sd/msx/config.txt` → `/sd/msx.ini` (SD card root). Existing cards need their config file moved/renamed.
- **Default HDMI baud rate lowered 10MHz → 8MHz**: real-hardware testing found 10MHz reliably corrupts the received palette on this wiring (e.g. white renders as green) — a genuine electrical/timing margin limit, not a transport bug. 5MHz and 8MHz were both confirmed clean (8MHz slightly faster); see `doc/hdmi_bridge_phase2_report.md`.

### Fixed (2026-09-05)

- **`MemoryError` on boot** after the above features were added (`msx_menu.py` grew ~21% from the new ROM browser + Display Settings code, enough to fail compiling on-device on a fresh boot): the Display Settings screen and the ROM folder browser were split into their own modules (`msx_display_settings.py`, `msx_rom_browser.py`) and are now imported lazily — only compiled the first time they're actually used, not during the eager boot-time import chain. `msx_menu.py` itself is now smaller than it was before any of this session's changes.
- **ROM browser crash (`UnicodeError`)** when a folder under the SD root contains a filename that isn't valid UTF-8 (e.g. left over from a different OS/filesystem): `uos.ilistdir()` raises `UnicodeError` while decoding it, which wasn't caught alongside the existing `OSError` handling and crashed the whole browse. Now caught the same way — that one directory is treated as unreadable/skipped rather than crashing.

### Added (2026-09-05/06)

- **LCD backlight control** (`msx.set_backlight()`): turned off automatically whenever `display=hdmi` (the LCD panel is still initialized but never rendered to in that mode, so it used to sit lit showing a stale/frozen image) — re-applied live whenever `display` changes via the HDMI Settings menu.
- **HDMI receiver hardware-reset line**: a spare sender GPIO (`HDMI_RESET_PIN` = GP13) wired directly to the receiver Pico 2's RUN pin, pulsed low briefly before `init_hdmi_output()` and whenever HDMI is turned on live from the menu. Fixes a real-hardware issue where the receiver can come up in a bad state if it's powered on (or hot-plugged) while the HDMI cable is already connected (suspected TMDS backfeed disturbing power-on-reset timing). Idle Hi-Z, matching `hdmi_bridge_receiver`'s `notes/sender_reset_line.md` design (no receiver-side firmware change needed).
- **60fps frame pacing**: the HDMI DMA optimization above regularly pushes non-Mega-ROM carts past 70fps on real hardware, which made MSX-clock time (fixed per `run_frame()` call) run ahead of wall-clock time — games played fast-forward and PSG audio pitched up. Each main-loop iteration now sleeps off whatever's left of a 1/60s budget; iterations already at/below 60fps (slower carts, `display=both`, etc.) are unaffected.
- **Per-cartridge rotating save states**: Save/Load State (both the runtime menu and the F5/F8 hotkeys) now key off the currently-loaded cart's own path (`cart_path`) instead of one shared file — each cart's saves sit next to its ROM (e.g. `/sd/games/Foo.ROM` → `Foo.0.sav`, `Foo.1.sav`, …), and up to `msx_menu.MAX_SAVE_SLOTS` (10) past states are kept per cart, rotated on every save. The runtime menu's "Load State" now opens a slot picker (`msx_save_slots.py`, lazily imported) instead of always loading the single most recent file; the F5/F8 hotkeys still always act on slot 0 (most recent) for quick-save/quick-load convenience.
- **Swap Cartridge now opens in the current cart's own folder** (`start_dir`) instead of always starting back at the SD root — the user can still navigate up past it (`..`) to the true root.

### Fixed (2026-09-06)

- **Swap Cartridge ESC regression** introduced by the `start_dir` feature above: when browsing opens below the SD root, a single ESC press used to walk up one folder level instead of cancelling (cancelling needed one ESC per level, back down to the root). ESC now always cancels immediately, regardless of depth — navigate up a level via `".."` + ENTER instead.
- **Runtime menu becoming permanently inaccessible after one `OSError(5,)` (EIO)**: `sdcard.py`'s `readblocks()`/`writeblocks()` raised `OSError(5)` straight from the first failed SD command response (a known real-hardware timing-margin issue on this shared SPI bus — see `lcd_suspend()`'s comment in `msx_menu.py`), which MicroPython's VFS layer then treated as fatal for the whole card: every subsequent SD access for the rest of the session failed the same way, even though the next SPI transaction on its own usually would have succeeded. Both methods now retry up to 3 times (5ms apart, re-issuing `spi.init()` each attempt) before giving up — turns a one-off marginal bus glitch back into a transient hiccup instead of a session-ending failure.

### Changed/Removed (2026-09-06)

- **LCD and HDMI output are now strictly mutually exclusive** — simultaneous output (`display=both`) has been removed entirely, not just discouraged, since switching SPI mode every frame between the two was already known to eventually corrupt/lose the HDMI signal and glitch the LCD on real hardware (see `hdmi_apply_spi_settings()` in `msx_core.c` and `doc/hdmi_bridge_phase2_report.md`). `display` now only accepts `lcd` (default) or `hdmi`.
- **Removed the separate `hdmi=0/1` config key and the HDMI Settings menu's "HDMI: On/Off" item**: with output now exclusive, `display=hdmi` alone both selects and enables the HDMI bridge — there was no longer a meaningful independent on/off state. HDMI hardware is initialized only when `display=hdmi` (at boot, or the moment the HDMI Settings menu's "Display" field is switched to `HDMI` live); the LCD panel is symmetrically lazy-initialized the moment it's switched back to `LCD`, so either direction works without a restart even though only one side is ever brought up at boot.
- **Removed the `boot_exclusive` config key and the Display Settings menu's "Exclusive Boot" item**: its behavior (skip the unused side's hardware init at boot) is now simply how `display=lcd`/`display=hdmi` always work — there's no longer a combined `both` mode for it to be an exception to.
- Existing `msx.ini` files with `hdmi=`/`boot_exclusive=`/`display=both` should drop the first two and change `display=both` to either `lcd` or `hdmi`; unrecognized/removed keys are otherwise just ignored by `load_config()`, so nothing breaks outright, but `display=both` now falls back to `lcd`.

### Added/Changed (2026-09-06, later same day)

- **Merged the "HDMI Settings" and "Display Settings" runtime menus into one "Display Settings" screen**: with output now strictly exclusive (see above), the old HDMI Settings screen had shrunk to just `Display`/`Frame Skip`, no longer justifying a separate menu item from the LCD panel/rotation/HDMI baud settings — both are edited from the same screen now (`msx_display_settings.py`).
- **New "Reinit \<LCD/HDMI\> now" action** on that screen: re-runs the active side's hardware init on demand, without a restart. Added after a real-hardware report of the HDMI picture going solid black during long play sessions and never recovering on its own, even though the runtime menu itself (which renders over a different, palette-independent send path) still displayed correctly — symptoms consistent with the HDMI receiver's color palette table (sent once, only at init) getting desynced somehow over a long session, which re-running the same init genuinely fixes by resending it, not merely resetting the transport. Reuses the same lazy-init callbacks the Display field itself calls when switched live, so it's exercised code either way.

### Fixed (2026-09-06, critical — boot hang with display=hdmi)

- **Board hangs completely on boot with `display=hdmi`** (serial output stops right after "HDMI bridge output enabled…", no ROM selector on either output, no further log lines at all — needs a hardware reset to recover): a regression from making LCD/HDMI output strictly exclusive earlier the same day. `msx->spi_inst` (the shared SPI peripheral instance every HDMI send function dereferences via `(spi_inst_t *)msx->spi_inst`, with no null check) was only ever set by `msx_init_display_hardware()` — the LCD path. A `display=hdmi` boot now always skips that function entirely, so `msx_init_hdmi_output()`'s first send (`msx_send_hdmi_palette()`) dereferenced a NULL SPI instance; `spi_write_blocking(NULL, …)` with no fault handler installed hangs the whole board rather than crashing cleanly. This gap technically predates today's change (an explicit `boot_exclusive=1`+`display=hdmi` combo hit it too), but was never actually exercised until `display=hdmi` skipping LCD init became the unconditional, normal path. Fixed by having `msx_init_hdmi_output()` set `msx->spi_inst = spi1` itself (this project always wires the HDMI bridge onto SPI1 regardless of which side owns the display at boot), independent of whether the LCD was ever initialized. **Firmware rebuild required** — this is a C-side fix (`src/msx/msx_core.c`).
- **Opening the runtime menu (GUI+F7) during a `display=hdmi` session drops the receiver to "No Signal"**: `msx_render_to_hdmi_raw332()` (the menu/UI send path — arbitrary colors outside the MSX's 16-entry hardware palette, so it can't reuse the palette-indexed path) had never been converted off the original fully-blocking, one-row-at-a-time `spi_write_blocking()` loop that `msx_render_to_hdmi()` itself moved away from back on 2026-09-04 — a full ~49KB blocking send, every single menu redraw. This project already had real-hardware precedent for exactly this failure mode (see `msx_clear_hdmi()`'s existing comment: a full blocking `PKT_FRAME` send "was also implicated in the receiver intermittently losing HDMI sync", which is why it uses a ~9-byte dedicated command instead). Converted to the same build-full-frame-then-one-DMA-transfer pattern as `msx_render_to_hdmi()`. Its new full-frame buffer (49152 bytes, 1 byte/pixel) shares storage with the existing palette-indexed one via a `union` (they're never both in use at once) — a first attempt giving it a fully separate buffer failed to link ("GcHeap is too small"), so growing this pair's combined footprint further isn't free on this board. **Firmware rebuild required.**
- **`MemoryError` at boot again** (`from msx_menu import (...)` in `main.py`, same failure point — and, on the first fix attempt below, the exact same 1336-byte allocation size — as an earlier session's `MemoryError`): `main.py` itself grew substantially across today's several rounds of changes (exclusive display, menu merge, new comments explaining each), pushing the combined peak (its own compiled footprint, still resident, plus `msx_menu.py`'s own compile-time cost right after) over the edge again — independent of `msx_menu.py`'s own size (which if anything *shrank* today from the HDMI/Display Settings merge).
  - First attempt: converted `main.py`'s module-level docstring and remaining function docstrings to plain `#` comments (a real docstring is compiled into a retained string constant; a `#` comment costs nothing at runtime). **Confirmed insufficient** — retesting on real hardware reproduced the identical error, byte-for-byte. On this board's non-compacting GC heap, freeing scattered small allocations elsewhere doesn't necessarily grow the single contiguous block a big compile actually needs — consistent with why the *original* version of this MemoryError (see the 2026-09-05 entry above) also needed more than trimming alone to fix.
  - Actual fix: extracted the runtime menu itself (`show_emulator_menu()`, `_show_audio_settings_menu()`, and their draw helpers — the single largest remaining eagerly-compiled chunk of `msx_menu.py`) into a new `msx_runtime_menu.py`, imported lazily the first time GUI+F7 is actually pressed, mirroring `msx_display_settings.py`/`msx_rom_browser.py`/`msx_save_slots.py`'s existing pattern exactly. `msx_menu.py`'s own eager footprint drops from ~42KB to ~29KB. `main.py`'s docstring-to-comment conversion is kept regardless (harmless and still a real, if smaller, saving). Pure MicroPython change, no firmware rebuild needed.
- **Picture corruption degrading into "No Signal" right after the boot-time ROM selector (`display=hdmi`)**: `msx_render_to_hdmi_raw332()`'s 2026-09-06 DMA conversion (see the "No Signal ... GUI+F7" fix above) left every menu/UI frame's DMA transfer in-flight, same as the game's own `msx_render_to_hdmi()` — a full ~49KB frame takes ~49ms to actually finish clocking out at 8MHz. Every caller that draws one of these screens and then immediately does SD-heavy work right after (the boot ROM selector → `load_cart_smart()`, folder navigation → the next directory listing, `msx_runtime_menu.py`'s "Loading…"/"Saving…" draws → cart/state I/O, `msx_display_settings.py`/Audio Settings → `save_config()`) was relying on `msx.wait_display()` or `hdmi_suspend()`'s own fixed 20ms settling pause to have finished it first — nowhere near enough for a ~49ms (or ~25ms for game-frame-sized) transfer. Worse, `msx_wait_display()` itself was guarded on `display_ready` only (an LCD-only flag, already flagged as a known gap in its own comment): with `display=hdmi` and no LCD ever initialized, calling it was a complete no-op, so the SD driver's `spi.init()` call could reconfigure the same physical SPI1 peripheral's baud/mode registers *while* the previous frame's DMA was still actively clocking bits out. First fix: also check `hdmi_ready` in `msx_wait_display()`'s guard (kept, still correct — safe now that `msx_init_hdmi_output()` unconditionally sets `msx->spi_inst`), plus an explicit `wait_display()`/`msx.wait_display()` call added at every site above that was missing one.
- **Simplified the fix above**: menu/UI screens have no FPS target to protect, unlike gameplay — there's no reason `msx_render_to_hdmi_raw332()` needed to leave anything in-flight at all in the first place. Reverted it to fully synchronous (one `spi_write_blocking()` call for the whole payload, blocking until genuinely done and CS deasserted before returning), which by construction makes every one of the explicit `wait_display()` calls added above redundant — removed all of them again except the two in `main.py`'s `save_state()`/`load_state()` (F5/F8 hotkeys), which guard against a *different*, still-real case: the game's own `msx_render_to_hdmi()` (gameplay frames) is still intentionally left in-flight for FPS, and F5/F8 can fire mid-gameplay. Net effect: one self-contained fix in `msx_core.c` instead of a call site to remember at every future menu screen. **Firmware rebuild required.**
- **`MemoryError` opening "Display Settings" from the runtime menu mid-gameplay**: unlike the boot-time `MemoryError`s above, this one's lazy import (`msx_display_settings.py`) now competes with a heap already fragmented by cart/emulation state (Mega ROM flash-cache, framebuffers, audio buffers, etc.), not just whatever main.py/msx_menu.py left behind at a fresh boot — the same module that compiles fine right after boot can still fail once real gameplay has been running for a while. Added an explicit `gc.collect()` right before each of the four lazy imports (`msx_rom_browser`, `msx_runtime_menu`, `msx_save_slots`, `msx_display_settings`) to defragment first, mirroring the same defensive pattern `msx_runtime_menu.py`'s own cart-loading code already used. Also converted `msx_display_settings.py`'s and `msx_runtime_menu.py`'s remaining docstrings to `#` comments as extra margin. Pure MicroPython change, no firmware rebuild needed.

### Added (2026-09-06, later still)

- **GUI+P / GUI+ESC global hotkeys** for the two most common `display=hdmi` recovery actions, reachable without ever opening the runtime menu (and so without importing `msx_runtime_menu.py`/`msx_display_settings.py` at all — cheaper on heap, and faster than navigating a menu when the goal is just "fix the picture"): GUI+P toggles `display` between `lcd`/`hdmi` live (same effect as Display Settings' "Display" field); GUI+ESC reinits whichever side is currently active in place (same effect as its "Reinit ... now" row) — the direct recovery action for the long-session HDMI "No Signal" issue. Both drain any in-flight DMA transfer first (`msx.wait_display()`) before reconfiguring the shared SPI1 peripheral, same reasoning as GUI+F7's existing guard.
